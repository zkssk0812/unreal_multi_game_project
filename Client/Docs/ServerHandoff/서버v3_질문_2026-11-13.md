v3.0 서버(`feature/pvpve-v3`, `3badc96`) 잘 받았습니다. 지난번 요청드린 내용이 거의 다 들어가 있어서, 이번부터는 **게임 규칙을 서버 기준으로 맞추고** 클라이언트를 프로토콜 v3.0으로 바꾸기로 했습니다.

## ★ 가장 먼저 확인 부탁드립니다 — 경비원 사격과 발견 방식
기획자분께서 경비원 기관총을 **대미지 10 × 초당 10발 = DPS 100**으로 정하신 것은 **"경비원의 명중률이 낮다"는 전제**였다고 합니다. 지금 서버는 타겟을 정확히 조준해서, 공격 범위 안에 1초만 서 있어도 HP 100이 모두 깎입니다. 그래서 아래 두 가지를 먼저 여쭙니다.

### 질문 A. 경비원 사격: 랜덤 난사 vs 정확 조준
| | 내용 |
|---|---|
| 기획 (팀 Q&A 15번 추가 설명 ③) | "매 공격을 할 때마다 **공격 범위에서 랜덤한 방향**으로 경비원이 공격을 가합니다." |
| 서버 (`GuardAI.cpp` `GuardShoot`, 293~301행) | 매 발 `YawTo(guard.pos, target.pos)`, 즉 **타겟 쪽 직선**으로 쏘고 처음 맞은 대상에 10 대미지 |

- 기획대로라면 한 발마다 공격 범위(부채꼴 60°) 안에서 방향을 무작위로 골라 쏘고, 그 직선에 걸린 대상만 맞게 됩니다.
- 기획 쪽 뜻이 이것이 맞는지 팀에서도 다시 확인하겠습니다. 정호님께서는 지금 구현이 의도하신 것인지, 랜덤 방향으로 바꾸는 것이 가능하신지 알려 주시면 감사하겠습니다.
- 클라이언트는 `SC_FIRE`의 `yaw`와 `hit_entity`를 그대로 그리므로, 서버가 바뀌어도 클라이언트는 고칠 것이 없습니다.
- 참고로 v3.0 서버에 클라이언트 봇 2명(무작위로 걷기만 함)을 붙여 5분 한 판을 돌려 보니, 경비원 사격이 108발 명중했고 두 명이 합쳐 **경비원에게 10번** 쓰러졌습니다(쓰러질 때마다 반납 금액 40% 손실). 지금 수치로는 경비원 시야에 잠깐만 들어가도 쓰러지는 느낌이라 공유드립니다.

### 질문 B. 경비원 발견 방식: 탐지 범위(원) vs 시야 부채꼴
| | 내용 |
|---|---|
| 기획 (팀 Q&A 15번 추가 설명 ①②) | ① "경비원의 **탐지 범위에 들어오는 순간** 경비원은 플레이어를 향해 회전 및 이동을 합니다. 최종적으로 타겟이 된 플레이어를 정면으로 바라보며, 0m까지 근접하는 게 목표입니다." ② "플레이어가 경비원의 **시야각에 들어오는 순간** 경비원은 공격을 시작합니다." |
| 서버 (`GuardAI.cpp` `CanSee` 348~358행, 사격 조건 156~176행) | 발견: 거리 15m **그리고** 시선 방향 좌우 45°(시야 90°) 안, 벽에 가리지 않을 때 / 사격: 타겟이 좌우 30°(공격 범위 60°) 안에 보일 때만 |

- 기획: 뒤에서 다가가도 탐지 범위(원) 안이면 경비원이 돌아서며 쫓아오고, 시야각(90°)에 들어오면 쏩니다.
- 서버: 시야 90° 안에 보여야 발견하고, 그중 60° 안일 때만 쏩니다. 뒤로 다가가면 들키지 않습니다.
- 어느 쪽으로 맞출지 팀에서 확인한 뒤 말씀드리겠습니다. 지금 서버 구현이 기획 그림(`경비원_범위`)을 보고 정하신 것이라면, 그림에서 읽으신 탐지 반지름 15m·공격 각도 60°의 근거도 알려 주시면 기획자분께 그대로 확인받겠습니다.

## ☆ 요청 2 — 상자를 맵 파일의 "상자 자리"에서 읽어 주세요
기획에서 상자 배치가 정해졌습니다(팀 Q&A 11월 13일 추가 답변).
- 상자는 **지정된 자리**에 놓습니다. **방마다 0~2개, 복도에는 두지 않습니다.** 최대 개수 = 지정된 자리 수입니다.
- 금고는 지정 자리 10곳(최소 4곳 이상이면 충분), 동시에 1개, 보물이 반납되면 직전 자리를 빼고 무작위 — 지금 서버와 같아서 바꾸실 것이 없습니다.

지금 서버는 상자를 방 안 무작위 20개로 두고 계셔서(psd 가정 A-02) 이 부분만 다릅니다. 아래처럼 바꿔 주실 수 있을까요?

| 항목 | 요청 |
|---|---|
| 처음 배치 | 맵 파일의 `box_slots` 자리마다 상자 1개 (무작위 20개 대신) |
| 다시 생김 | 지금처럼 부서진 **같은 자리**에 30~60초 뒤 |
| `box_slots`가 없거나 비어 있을 때 | 지금처럼 방 안 무작위 20개 (옛 맵 파일도 그대로 실행되도록) |
| 드롭·HP·작업 시간 | 지금 그대로 |

**데이터 형식** — 금고 자리(`vault_slots`)와 같은 모양으로 맞춰 v3 맵 파일에 넣었습니다. 이름이나 항목은 정호님께서 읽기 편하신 대로 바꾸셔도 됩니다(말씀해 주시면 파일을 고쳐 드리겠습니다).
```json
"box_slots": [
  { "id": "box_slot_01", "client": "Box_01", "room": "Room_02", "pos": [7164.0, -90.0, 0.0], "yaw": 0.0 },
  { "id": "box_slot_02", "client": "Box_02", "room": "Room_02", "pos": [8730.0, -861.0, 0.0], "yaw": 0.0 },
  …(20곳)
]
```
| 항목 | 뜻 |
|---|---|
| `id` | 자리 이름 (`box_slot_01`부터) |
| `client` | 저희 레벨의 표시용 이름 (서버는 안 쓰셔도 됩니다) |
| `room` | 놓인 방의 `rooms[].id` (복도는 없습니다) |
| `pos` | 상자 중심의 바닥 위치 `[x, y, z]` cm (지금 상자 엔티티 위치와 같은 기준) |
| `yaw` | 상자 방향(도). 판정에 쓰지 않으시면 무시하셔도 됩니다 |

**상자 자리 20곳** — 그림: `Docs/ServerHandoff/상자_자리_제안.png` (초록 번호 = 상자, 주황 번호 = 금고 후보)

| 개수 | 방 | 기준 |
|---|---|---|
| 2개 | 2, 14, 21, 29 | 넓은 방 |
| 1개 | 5, 6, 8, 10, 16, 18, 23, 24, 26, 27, 31, 32 | 금고 후보가 없는 방 |
| 0개 | 금고 후보 방 10곳(1, 4, 7, 12, 17, 19, 25, 28, 30, 33), 큰 홀(15)·현관(3)·통로 방(9, 22), 문 없는 방(11, 13, 20) | |

- 지금 서버의 상자 수(20개)와 같게 맞췄습니다. 모든 자리는 벽에서 80cm 띄운 방 구석이고(상자 반지름 50cm 기준), 금고 후보와 5m 이상 떨어져 있습니다.

## 2. 서버 코드를 읽고 이해한 내용 (맞는지 확인 부탁드립니다)
1. 이동은 클라이언트가 하고, 서버는 `CS_MOVE`의 위치를 그대로 씁니다(속도·벽 검사, 보정 패킷 없음). `yaw`는 커서 방향이며 공격·스킬 방향으로 쓰입니다.
2. 경직(Stunned) 중에도 서버는 이동 패킷을 받습니다. 그래서 **경직·끈끈이 감속·은신 감속·레일건 잠금·제트팩 이동·밀려남은 클라이언트가 스스로 적용**합니다.
3. 은신·연막 안의 대상, 퍽이 없는 사람의 경비원·플레이어 위치도 서버는 모두 보내고, 숨기는 것은 클라이언트가 합니다.
4. 구르기는 서버가 SP와 0.5초 무적만 처리하고, 실제 이동은 클라이언트가 합니다.
5. 금고를 열면 금고 자리에 보물(Valuable, Unique) 엔티티가 따로 생기고, 그 엔티티를 대상으로 `InteractBegin`을 보내 줍습니다. 새 금고는 보물이 **반납된 뒤** 생깁니다.
6. 게임이 끝나면 15초 뒤 또는 `CS_RETURN`으로 **로비**로 돌아가고, 방은 없어집니다(대기실 복귀 없음).
7. 방은 1명으로도 시작됩니다(전원 준비 = 혼자 준비).
8. 로비·방 요청의 빈도 제한은 지금 서버에 없습니다.

## 3. 여쭤보고 싶은 것
1. **무기 칸이 꽉 찼을 때 교체되는 칸**: 지금은 든 무기와 관계없이 항상 0번 칸(`weapons[0]`)이 교체됩니다(`WorldItems.cpp` 85~91행). 기획 UI에서는 "무기1 = 지금 들고 있는 무기"로 보여서, 1번 칸을 들고 있을 때는 **안 들고 있는 쪽**이 바뀌게 됩니다. 의도하신 동작인지요? 화면의 "무기1" 칸을 `active_slot` 기준으로 그릴지, 0번 칸 기준으로 그릴지 정하려고 합니다.
2. **`SC_INTERACT.duration_ms`와 작업 속도**: `protocol.h` 주석대로 `duration_ms`는 작업 속도 1.0 기준(10000/3000)으로 오고, 유용한 도구 퍽이 있으면 진행이 1.1배로 빨라지는 것으로 이해했습니다. 진행 막대는 클라이언트가 방 상태의 퍽 목록을 보고 1.1배로 계산하면 될까요? (psd 3.4에는 "duration은 작업 속도 반영"이라고 되어 있어서 확인드립니다.)
3. **기사회생 발동 시 `SC_DAMAGE`**: HP 1로 버틸 때 `hp_after`가 0으로 오고 `SC_DOWNED`는 오지 않는 것으로 보입니다. 다른 플레이어 화면에서는 HP가 0으로 보였다가 스냅샷으로 1이 됩니다. 의도하신 것인지요?
4. **달리기 상태**: 달리는 중에 `CS_MOVE`가 멈추면 Running이 남아 SP가 계속 줄어드는 것으로 보입니다. 클라이언트는 멈출 때 플래그 0인 이동 패킷을 한 번 더 보내고 1초마다도 보내니 문제는 없을 것 같은데, 혹시 다른 주의점이 있을까요?
5. **상호작용 중 공격 키**: `InteractBegin`이 `attackHeld`를 지우지 않아서, 공격 키를 누른 채 F를 누르면 작업 중에도 계속 발사되는 것으로 보입니다. 의도하신 동작인지요?
6. **시험용 게임 시간**: 게임 시간을 줄이려면 다시 빌드해야 하는 것으로 이해했습니다. 서버 코드는 저희가 고치지 않기로 해서, 가능하시다면 `server_config.json`이나 실행 옵션으로 게임 시간·결과 화면 시간을 바꿀 수 있게 해 주시면 끝까지 가는 시험이 훨씬 빨라집니다. (급하지 않습니다.)
7. **반납지점 5곳이 동시에 이동**: 시작할 때 5곳이 함께 생겨서 아무도 쓰지 않으면 60초에 5곳이 한꺼번에 옮겨집니다. 의도하신 것인지요?
8. **은신 감속 수치**: "이동 속도 80% 감소"를 원래 속도 × 0.2로 적용하려고 합니다. 맞을까요?
9. **높이(z)**: 스폰·리스폰·아이템 위치는 바닥(z = 0) 기준이고 `CS_MOVE.pos`도 발 위치로 보내고 있습니다. 지금처럼 발 위치로 보내면 되는지요?
10. **필드 아이템 생성 지점**: psd 8장에 "맵 데이터 요청(없으면 서버가 방 안에서 무작위)"라고 되어 있습니다. 상자는 위 ☆ 요청으로 따로 정리했고, 필드 아이템 자리는 기획에서 아직 정해지지 않아 지금처럼 무작위로 두시면 됩니다. 정해지면 같은 방식으로 맵 파일에 넣어 전달드리겠습니다.
