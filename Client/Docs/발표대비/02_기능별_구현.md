## 1. 메뉴·로비 흐름

### ① 기획 요구사항
- 화면 흐름: **메인화면 → 로그인 → 로비(방 목록) → 대기실 → 게임 → 결과창 → 대기실/로비** (CLAUDE.md 1차 마일스톤).
- 로그인: 이름만, **영문자 2~12자**(사용자 결정 — 서버는 48바이트·한글 허용). 로비: 방 목록·검색·방 만들기·입장·**빠른 찾기**. 대기실: 캐릭터·퍽 선택, 전원 준비 시 자동 시작(시작 버튼 없음).
- 게임 종료(프로그램 종료)는 메인화면에서만.

### ② 구현 방식
| 역할 | 클래스 | 파일 |
|---|---|---|
| 연결·단계·방 상태를 **게임 내내** 들고 있는 관리자 | `UVHNetSubsystem` (GameInstance 서브시스템) | `Network/VHNetSubsystem.h/.cpp` |
| 화면 전환 담당 | `AVHMenuPlayerController` | `Game/VHMenuPlayerController.cpp` |
| 화면(위젯) 공통 부모 | `UVHScreenWidget` (UMG `UUserWidget` 상속) | `UI/VHScreenWidget.h` |
| 각 화면 | `UVHMainMenuWidget`, `UVHLoginWidget`, `UVHLobbyWidget`, `UVHRoomWidget`, `UVHResultWidget` + 블루프린트 `WBP_MainMenu/Login/Lobby/Room/Result` | `UI/*.cpp`, `Content/VaultHeist/UI/` |

흐름: 위젯 버튼 → `UVHNetSubsystem`의 요청 함수(`ConnectAndLogin`, `RequestRoomList`, `CreateRoom`, `JoinRoom`, `QuickFind`, `SetReady` …) → 패킷 전송 → 응답 패킷 처리(`HandleLogin`, `HandleRoomState` …) → `SetPhase()`가 단계를 바꾸고 `OnPhaseChanged` 델리게이트 방송 → `AVHMenuPlayerController::HandlePhaseChanged`가 화면을 바꾼다.
위젯은 C++ 클래스에 `UPROPERTY(meta = (BindWidget))` 로 버튼·글자를 선언하고, 같은 이름의 위젯을 WBP에 배치해 연결한다(예: `UI/VHLobbyWidget.h`의 `PrimaryQuickFindButton`, `RoomListBox`).

### ③ 핵심 코드
`Game/VHMenuPlayerController.cpp` — `AVHMenuPlayerController::HandlePhaseChanged`
```cpp

{
case EVHNetPhase::Lobby:
    ShowScreen(EVHScreen::Lobby);
    break;
case EVHNetPhase::Room:
    ShowScreen(EVHScreen::Room);
    break;
```
- 네트워크 **단계(Phase)** 가 바뀌면 그 단계에 맞는 화면을 띄운다. 화면이 서버 상태를 따라가므로 "화면과 서버 상태가 어긋나는" 일이 줄어든다.

`AVHMenuPlayerController::ShowScreen`
```cpp
// 버튼 클릭·키 입력을 처리하는 도중에 그 버튼이 속한 화면을 지우면, … 그래서 실제 전환은 다음 틱에 한다.
GetWorldTimerManager().SetTimerForNextTick(FTimerDelegate::CreateWeakLambda(this, [this, Screen]()
{
    …
    CurrentWidget = CreateWidget<UVHScreenWidget>(this, Class);
    CurrentWidget->AddToViewport(0);
```
- 화면 전환을 **다음 프레임으로 미룬다**. 버튼 이벤트 처리 중에 그 버튼이 속한 위젯을 지우면 같은 입력이 새 화면으로 이어지거나 지운 위젯을 건드릴 수 있어서다(문제 해결 사례는 `03_문제해결_사례.md`).
- `CreateWeakLambda(this, …)`: 컨트롤러가 그 사이 사라지면 람다가 실행되지 않는다(약한 참조).

`Network/VHNetSubsystem.cpp` — `UVHNetSubsystem::ValidateLoginName`
```cpp

if (!bAlpha) { … return false; }
if (Name.Len() < 2) { … return false; }
if (Name.Len() > 12) { … return false; }
```

- 글자마다 영문자인지 검사 → 공백·숫자·그 밖의 문자마다 다른 안내 문구. 로그인 위젯이 입력할 때마다 이 함수를 불러 [확인] 버튼을 켜고 끈다.

`UVHNetSubsystem::QuickFindOnList` (빠른 찾기 — 전용 패킷이 없어서 클라이언트가 조합)
```cpp

Candidates.Sort([](const FVHRoomSummary& A, const FVHRoomSummary& B) { return A.PlayerCount > B.PlayerCount; });
```

- 방 목록에서 들어갈 수 있는 방(대기중 + 빈자리)만 골라 **사람이 많은 방부터** 시도한다. 입장 실패(RoomFull 등)면 `QuickFindTryNext`가 다음 후보, 후보가 없으면 `QuickFindCreate`가 기본 설정으로 방을 만든다.

게임 시작·끝: `UVHNetSubsystem::HandleGameLoad` → `SetPhase(EVHNetPhase::Game)` → `OpenGameLevel()`(설정의 `GameLevel` = `L_Mansion_1F`). 게임이 끝나면 `HandleGameEnd`가 결과를 `LastGameEnd`에 저장하고 `OpenMenuLevel()` → 메뉴 레벨이 열리면 결과창.

### ④ 왜 이렇게 설계했나
- **GameInstance 서브시스템**은 레벨을 바꿔도(메뉴 ↔ 게임) 사라지지 않는다. 연결·로그인 정보·방 상태는 레벨이 바뀌어도 유지돼야 하므로 여기에 둔다.
- 화면은 **단계(Phase) 하나만 보고** 결정한다 → 상태가 한 곳에 모여 있어 디버깅이 쉽다(상태 머신).
- UI 디자인이 미정이라 **로직은 C++, 배치는 WBP(BindWidget)** 로 나눴다. 디자이너가 WBP만 바꿔도 동작은 유지된다.

### ⑤ 다른 방법과 비교
| 방법 | 장점 | 단점 |
|---|---|---|
| (채택) 서브시스템 + 단계 기반 화면 전환 | 상태 한 곳, 레벨 이동에도 유지 | 단계가 늘면 switch가 커짐 |
| 위젯마다 직접 다음 화면을 띄움 | 처음엔 간단 | 서버 응답과 화면이 어긋나기 쉬움 |
| 화면을 레벨로 나눔 | 화면별 독립 | 레벨 로딩 비용, 상태 전달 번거로움 |

### ⑥ 한계·개선
- UI는 임시 디자인(색·폰트는 `DA_VHUIStyle`에 모음). 설정 화면은 자리만 있음.
- 캐릭터·퍽 목록은 임시 데이터(`DA_VHGameData`, 의적 A/B/C, 퍽 1~6) — 기획 미정.
- 방 목록 페이지 시작 번호 등 서버와 확인할 것은 `04_서버연동과_역할분담.md`.

## 2. 네트워크

### ① 기획 요구사항 (CLAUDE.md "서버 프로토콜")
- TCP, 포트 9000, 패킷 = **`[size:uint16][type:uint16][body]`**(리틀 엔디언, size는 헤더 포함 전체), `#pragma pack(1)` 구조체를 그대로 memcpy.
- size < 4 또는 > 8192면 서버가 끊는다. 가변 길이 패킷은 `*_Size(count)`로 검사.
- **2초마다 `CS_PING`**(10초 응답 없으면 서버가 끊음), `SC_PONG`으로 RTT·서버 시각.
- **단계별로 보낼 수 있는 패킷이 정해져 있고**, 어기면 서버가 끊는다 → 클라이언트도 단계를 추적.
- 로비·방 요청은 초당 10회 제한.
- 서버가 아직 PING/PONG만 구현 → **가짜 서버(Mock)** 와 **진짜 TCP** 전송을 설정으로 바꿔 쓸 수 있게.

### ② 구현 방식 — 계층 구조
```
[UI 위젯] ─요청─▶ UVHNetSubsystem ──SendPacket/SendBytes──▶ IVHTransport ─┬─ FVHTcpTransport (FSocket, 진짜 서버)
                    ▲  CanSend(단계 검사)·PassRateLimit                       └─ FVHMockTransport → FVHMockServer (같은 프로세스)
                    │
   OnBytes ─▶ FVHPacketAssembler(재조립) ─▶ HandlePacket(디스패처) ─▶ HandleLogin/HandleRoomState… ─▶ 델리게이트 방송 ─▶ UI
```
| 파일 | 역할 |
|---|---|
| `Network/Protocol/protocol.h` | 서버 팀원의 프로토콜 정의(**v1.0**, 내용 수정 금지) |
| `Network/VHProtocol.h` | `namespace RobProto { #include "Protocol/protocol.h" }` 래퍼 — 언리얼 이름과 충돌 방지 |
| `Network/VHPacket.h/.cpp` | `VHPacket::Make/ToBytes/ReadFixed/ReadVariable`, 문자열 변환, `FVHPacketAssembler` |
| `Network/VHTransport.h` | 전송 인터페이스 `IVHTransport` |
| `Network/VHTcpTransport.cpp` | `FVHTcpTransport` — 논블로킹 소켓, Tick에서 폴링 |
| `Network/VHMockTransport.cpp`, `VHMockServer.cpp` | 가짜 서버 |
| `Network/VHSettings.h` | `bUseMockServer`(기본 true), `ServerHost`(127.0.0.1), `ServerPort`(9000) — `Config/DefaultGame.ini`에서 바꿈 |

> 서버 팀원 저장소는 2026-10-26 기준 **프로토콜 v2.0**으로 올라갔다. 클라이언트는 아직 v1.0 사본을 쓴다 → 바뀌는 점은 `04_서버연동과_역할분담.md`.

### ③-1 패킷 만들기·읽기 — `Network/VHPacket.h`
```cpp
template <typename T>
T Make(RobProto::PacketId Id)
{
    static_assert(std::is_trivially_copyable_v<T>, "패킷 구조체는 memcpy 가능한 POD여야 한다");
    T Packet{};
    Packet.size = static_cast<uint16_t>(sizeof(T));
    Packet.type = Id;
    return Packet;
}
```
- `static_assert`: 컴파일할 때 "그대로 복사해도 되는 구조체인지" 검사(포인터·가상함수가 있으면 컴파일 오류).
- `T Packet{}`: 0으로 초기화 → 보내지 않은 칸에 쓰레기 값이 안 들어간다.
- `size`(헤더 포함 전체 길이)와 `type`(패킷 번호)을 채운다 = 패킷의 **[size][type]** 부분.

```cpp
template <typename T>
bool ReadFixed(const uint8* Data, int32 Size, T& Out)
{
    if (Size != static_cast<int32>(sizeof(T))) { return false; }
    FMemory::Memcpy(&Out, Data, sizeof(T));
    return true;
}
```
- 고정 길이 패킷은 **받은 크기 == 구조체 크기**일 때만 복사. 다르면 버리고 로그(`HandlePacket`의 `Bad()`).
- 가변 길이(`ReadVariable`)는 `count <= MaxCount` 이고 `Size == SC_RoomList_Size(count)` 인지까지 검사한다.

### ③-2 TCP 스트림 재조립 — `FVHPacketAssembler::Pop` (`Network/VHPacket.cpp`)
```cpp
const int32 Available = Buffer.Num() - ReadPos;
if (Available < VHPacket::HeaderSize) { return EResult::NeedMore; }
const uint8* Head = Buffer.GetData() + ReadPos;
const int32 Size = static_cast<int32>(Head[0]) | (static_cast<int32>(Head[1]) << 8);	// 리틀 엔디언 uint16
if (Size < VHPacket::MinPacketSize || Size > VHPacket::MaxPacketSize) { return EResult::Error; }
if (Available < Size) { return EResult::NeedMore;	// 패킷 일부만 도착 → 나머지를 기다린다 }
OutPacket.Reset(Size);
OutPacket.Append(Head, Size);
ReadPos += Size;
```
- 줄 1–2: 헤더(4바이트)도 다 안 왔으면 더 기다린다.
- 줄 4: 앞 2바이트를 **리틀 엔디언**으로 읽어 패킷 길이를 안다(낮은 바이트가 먼저).
- 줄 5: 4 미만·8192 초과면 **오류 → 연결 끊기**(명세와 같음).
- 줄 6: 길이만큼 다 안 모였으면(패킷이 **잘려 옴**) 기다린다.
- 줄 7–9: 한 패킷을 꺼내고 읽은 위치를 옮긴다. 여러 패킷이 **붙어 와도** 호출한 쪽이 `NeedMore`가 나올 때까지 반복해서 꺼낸다.

호출하는 쪽 — `UVHNetSubsystem::OnBytes`
```cpp
Assembler.Append(Data, Num);
for (;;)
{
    const FVHPacketAssembler::EResult R = Assembler.Pop(Packet);
    if (R == FVHPacketAssembler::EResult::NeedMore) { return; }
    if (R == FVHPacketAssembler::EResult::Error) { … HandleTransportClosed(…); return; }
    HandlePacket(Packet.GetData(), Packet.Num());
```
- 받은 바이트를 쌓고 → 완성된 패킷이 없을 때까지 꺼내서 → `HandlePacket`(패킷 종류별 `switch` = **디스패처**)으로 보낸다.
- 버퍼는 다 읽으면 비우고, 읽은 앞부분이 16KB를 넘으면 정리한다(무한히 커지지 않게).

TCP 수신 — `FVHTcpTransport::Tick` (`Network/VHTcpTransport.cpp`)
```cpp
// 받을 수 있는 만큼 모두 읽는다. 패킷 경계는 신경 쓰지 않는다(위에서 재조립).
for (;;)
{
    int32 Read = 0;
    const bool bOk = Socket->Recv(RecvScratch.GetData(), RecvScratch.Num(), Read);
    if (!bOk) { CloseSocket(); if (OnDisconnected) OnDisconnected(…); return; }
    if (Read <= 0) { break;	// 지금은 더 받을 데이터 없음 }
    if (OnBytesReceived) OnBytesReceived(RecvScratch.GetData(), Read);
```
- 소켓은 `SetNonBlocking(true)`(논블로킹)이라 `Recv`가 기다리지 않는다. **별도 수신 스레드 없이 게임 스레드의 Tick에서 폴링**한다 → 받은 패킷을 게임 스레드에서 바로 처리할 수 있어 스레드 동기화가 필요 없다.
- `UVHNetSubsystem`은 `FTSTicker::GetCoreTicker().AddTicker(…)`로 매 프레임 `Tick`을 받는다(`Initialize`).

### ③-3 단계별 패킷 제한 — `UVHNetSubsystem::CanSend`
```cpp
if (Id == PacketId::CS_PING) { return Phase >= EVHNetPhase::Anonymous; }
switch (Phase)
{
case EVHNetPhase::Anonymous:
    return Id == PacketId::CS_LOGIN;
case EVHNetPhase::Lobby:
    return Id == PacketId::CS_GET_PROFILE || … || Id == PacketId::CS_CREATE_ROOM || Id == PacketId::CS_JOIN_ROOM;
case EVHNetPhase::Room: …
case EVHNetPhase::Game:
    return Id == PacketId::CS_LOAD_COMPLETE || Id == PacketId::CS_MOVE || Id == PacketId::CS_ACTION || Id == PacketId::CS_RETURN;
```
- 단계 목록 `EVHNetPhase`(`Network/VHNetTypes.h`): `Disconnected → Connecting → Anonymous → Authenticating → Lobby → Room → Game`.
- `SendBytes`가 보내기 전에 `CanSend`를 확인하고, 허용 안 되면 **보내지 않고 경고 로그**("단계 %d에서 허용되지 않은 패킷 … 전송을 막았습니다"). 서버가 끊기 전에 클라이언트가 먼저 막는다.
- 같은 함수에서 로비·방 요청(번호 1000~2999)은 `PassRateLimit()` — 최근 1초 요청이 **8번**(`RequestLimitPerSecond = 8`, 서버 10회보다 여유)이면 막고 "요청이 너무 잦습니다" 안내.
- 가짜 서버도 `FVHMockServer::ReceivePacket`에서 `IsAllowed(Id)`가 아니면 진짜 서버처럼 `Kick(KickReason::ProtocolViolation, …)` → 자동화 테스트 `VaultHeist.Net.MockServerFlow`가 이 경우를 일부러 확인한다.

```cpp
RttMs = static_cast<int32>(FMath::Max<int64>(0, Now - static_cast<int64>(P.client_time_ms)));
// 서버 시각 ≈ 받은 server_time + RTT/2
ServerTimeOffsetMs = static_cast<int64>(P.server_time_ms) + RttMs / 2 - Now;
```
- 접속하면 바로 한 번, 그 뒤 **2초마다** PING(모든 단계에서 허용). PONG에 내가 보낸 시각이 돌아오므로 **왕복 시간(RTT)** = 지금 − 보낸 시각.
- 서버 시각 추정 = 서버가 적은 시각 + RTT/2(가는 데 절반 걸렸다고 가정).
- 클라이언트 쪽 끊김 감지: 아무 데이터도 **15초**(`ReceiveTimeoutSeconds = 15.0`) 못 받으면 끊긴 것으로 처리. 서버의 10초 기준과는 별개로, 클라이언트가 늦게라도 알아차리게 한 값.

### ③-5 전송 계층 교체 — `IVHTransport` (`Network/VHTransport.h`)
```cpp
class IVHTransport
{
public:
    virtual void Connect(const FString& Host, int32 Port) = 0;
    virtual void Disconnect() = 0;
    virtual bool Send(const TArray<uint8>& Bytes) = 0;
    virtual void Tick(float DeltaSeconds) = 0;
    …
    TFunction<void(const uint8* Data, int32 Num)> OnBytesReceived;
```
`UVHNetSubsystem::ConnectAndLogin`
```cpp
bUsingMock = S.bUseMockServer;
if (bUsingMock) { … Transport = MakeUnique<FVHMockTransport>(Config, S.bMockSplitPackets); }
else            { Transport = MakeUnique<FVHTcpTransport>(S.ConnectTimeoutSeconds); }
```
- 서브시스템은 **"바이트를 보내고 받는다"는 인터페이스만** 알고, 실제 대상은 설정(`bUseMockServer`) 하나로 바뀐다. 패킷 조립·재조립·해석은 둘이 공유 → 가짜 서버로 시험한 코드가 그대로 진짜 서버에도 쓰인다.
- 가짜 서버는 받은 바이트를 진짜 서버처럼 해석하고 **같은 형식의 SC_ 바이트**를 돌려준다. 그리고 `bMockSplitPackets`(기본 true)면 응답을 **1~97바이트 조각으로 일부러 잘라** 보낸다(`FVHMockTransport::Tick`의 `FMath::RandRange(1, FMath::Min(ToClient.Num(), 97))`) → 재조립 코드가 항상 실전처럼 시험된다.

### ④ 왜 이렇게 설계했나
- 서버가 아직 로그인·방을 구현하지 않아도 **UI 흐름 전체를 먼저 완성**하려면, 프로토콜대로 응답하는 가짜 서버가 필요했다. 바이트 단위로 같게 만들었기 때문에 실서버로 바꿀 때 바뀌는 건 전송 계층뿐이다.
- TCP는 메시지 경계가 없는 **바이트 스트림**이다 → 헤더의 size로 직접 잘라야 한다(재조립기).
- 수신을 별도 스레드 대신 Tick 폴링으로 → 언리얼 객체(UI·액터)는 게임 스레드에서만 안전하게 다룰 수 있으므로 동기화 문제를 원천 차단.

### ⑤ 다른 방법과 비교
| 주제 | 채택 | 대안 | 비교 |
|---|---|---|---|
| 직렬화 | `#pragma pack(1)` 구조체 memcpy | protobuf·FlatBuffers | 빠르고 서버와 같은 헤더를 공유. 대신 엔디언·구조체 배치가 같아야 함(둘 다 x64 리틀 엔디언) |
| 수신 | 논블로킹 + Tick 폴링 | 수신 스레드 + 큐 | 폴링은 단순·안전, 프레임마다 확인하므로 최대 1프레임 지연. 스레드는 지연이 적지만 큐·락 필요 |
| 가짜 서버 | 인프로세스 Mock | 서버 완성 대기 / 별도 테스트 서버 | Mock은 혼자 개발 가능, 대신 규칙을 두 번 짜야 하고 실서버와 다를 위험 |
| 단계 제한 | 클라이언트도 검사 | 서버만 검사 | 이중 검사로 버그를 일찍 발견(서버에 끊기기 전에 로그) |

### ⑥ 한계·개선
- 게임 중 패킷(`CS_MOVE`, `C_ACTION`, 스냅샷)은 **아직 처리하지 않는다**(`HandlePacket`의 `default`에서 무시). 게임 규칙은 지금 클라이언트가 판정(8장의 Authority).
- 실서버로는 접속 + PING/PONG까지만 확인 가능(서버가 그 당시 PING만 구현). v2 서버와 연결은 `04` 참고.
- `CS_LOAD_COMPLETE`의 `map_hash`는 서버가 준 값을 그대로 돌려보낸다(가정, `OnPostLoadMap` 주석) — 확인 필요.

## 3. 탑뷰 카메라와 벽 투명 처리

### ① 기획 요구사항
- **탑뷰 고정 카메라**(팀 결정), 회전 없음. 어두운 저택 + 손전등.
- 저택 맵에서 카메라 쪽 벽 뒤에 서면 캐릭터가 **완전히 가려지는 문제**를 PIE에서 확인 → 사용자 결정: **카메라와 내 캐릭터 사이 벽만 투명하게**.

### ② 구현 방식
- 카메라: `UVHAimComponent::ApplyTopDownCamera` (`Gameplay/VHAimComponent.cpp`)가 캐릭터의 스프링암을 **절대 회전**(피치 -65°, 거리 1500cm, FOV 70)으로 고정.
- 벽 투명: 벽 재질 `M_VHWallFade`(Masked) + 재질 파라미터 모음 `MPC_VHOcclusion`(`PlayerPos`, `Radius`, `Enabled`). 매 프레임 `UVHAimComponent::UpdateOcclusion`이 내 캐릭터 위치를 MPC에 넣고, 재질의 **Custom 노드(HLSL)** 가 "카메라→캐릭터 선 주변 반경 150cm 안, 캐릭터보다 카메라 쪽" 벽 픽셀을 지운다. 바닥은 이 재질을 쓰지 않으므로 사라지지 않는다.

### ③ 핵심 코드
`UVHAimComponent::ApplyTopDownCamera`
```cpp
Arm->bUsePawnControlRotation = false;
Arm->bInheritPitch = false;
Arm->bInheritYaw = false;
Arm->bInheritRoll = false;
Arm->SetUsingAbsoluteRotation(true);
Arm->SetWorldRotation(FRotator(C.CameraPitch, 0.f, 0.f));
Arm->TargetArmLength = C.CameraDistance;
Arm->bDoCollisionTest = false;	// 벽 때문에 카메라가 캐릭터 쪽으로 당겨지지 않게
```
- 스프링암이 캐릭터·컨트롤러 회전을 **따르지 않게** 하고 월드 기준 각도로 고정 → 캐릭터가 돌아도 화면은 돌지 않는다. 화면 위 = 월드 +X.
- `bDoCollisionTest = false`: 3인칭 기본값이면 벽에 걸릴 때 카메라가 당겨져 들어오는데, 탑뷰에서는 오히려 방해라 끈다.

`UVHAimComponent::UpdateOcclusion`
```cpp
UKismetMaterialLibrary::SetScalarParameterValue(World, Collection, TEXT("Enabled"), C.bWallOcclusionFade ? 1.f : 0.f);
UKismetMaterialLibrary::SetScalarParameterValue(World, Collection, TEXT("Radius"), C.OcclusionRadius);
UKismetMaterialLibrary::SetVectorParameterValue(World, Collection, TEXT("PlayerPos"), FLinearColor(GetOwner()->GetActorLocation()));
```
- MPC는 **모든 재질이 함께 읽는 전역 값**이다. 위치 하나만 매 프레임 바꾸면 벽 전체에 적용된다(재질 인스턴스를 벽마다 만들 필요 없음). 에디터에서는 `Enabled` 기본값이 0이라 벽이 멀쩡히 보인다.

`M_VHWallFade` 의 Custom 노드 코드(에셋 그래프에 들어 있는 HLSL — 2026-10-26 에디터에서 직접 읽어 아래와 같음을 확인. 재질 더블클릭 → Custom 노드 → 디테일 패널 Code에서 볼 수 있다)
```hlsl
float3 d = Pl - Cam;  float L = max(length(d), 1.0);  float3 n = d / L;   // 카메라→캐릭터 방향
float3 rel = W.xyz - Cam;
float t = dot(rel, n);                        // 이 픽셀이 그 선을 따라 얼마나 앞에 있나
float r = length(rel - n * t);                // 선에서 떨어진 거리
if (E < 0.5 || t > L - 40.0) return 1.0;      // 꺼짐 / 캐릭터보다 뒤쪽 벽 → 보임
if (r >= R) return 1.0;                       // 반경 밖 → 보임
if (r >= R - 40.0) { float2 px = floor(Parameters.SvPosition.xy); return fmod(px.x + px.y, 2.0); }  // 가장자리 40cm 체크무늬
return 0.0;                                   // 안쪽 → 지움(Opacity Mask 0)
```
- 입력: `W`=픽셀의 월드 위치(WorldPosition), `C`(Cam)=카메라 위치(CameraPositionWS), `Pp`(Pl)=MPC PlayerPos, `R`=Radius, `E`=Enabled.
- 원리는 "**점과 직선 사이 거리**": 카메라에서 캐릭터로 가는 선분 주변의 원기둥 안에 든 벽 픽셀만 지운다. `t > L-40`(캐릭터보다 뒤)인 벽은 가리지 않으므로 남긴다.
- 가장자리 40cm는 화면 픽셀 위치로 **체크무늬(디더)** 를 만들어 경계가 덜 딱딱하게.

### ④ 왜 이렇게 설계했나
- 카메라 -65°에서 3m 벽은 뒤쪽 약 1.4m(= 3 / tan65°)를 가린다. 캐릭터가 그 안에 서면 완전히 사라짐 → 캡처로 확인 후 사용자에게 선택지를 줌(투명 처리 / 카메라 각도 / 둘 다 / 보류) → "캐릭터 앞 벽만 투명" 선택.
- 충돌·손전등 빛·소리는 그대로 두고 **보이는 것만** 바꾸는 방법이라 게임 규칙에 영향이 없다.

### ⑤ 다른 방법과 비교
| 방법 | 장점 | 단점 |
|---|---|---|
| (채택) 재질에서 선분 주변 픽셀 지우기 | 벽 메시 1개여도 됨, 규칙 영향 없음, 비용 작음 | 벽 재질을 반드시 이 재질로 써야 함 |
| 카메라 각도를 더 위로(-80°) | 데이터 1개만 바꿈 | 여전히 일부 가림, 화면이 평면도처럼 납작 |
| 라인 트레이스로 가리는 벽 액터를 숨김 | 이해 쉬움 | 맵이 메시 1개라 벽 전체가 사라짐 |
| 캐릭터 실루엣을 벽 위에 그림 | 벽 유지 | 벽 뒤 오브젝트(금고 등)는 여전히 안 보임 |

### ⑥ 한계·개선
- **내 캐릭터만** 투명 처리(다른 의적·경비원 앞 벽은 그대로).
- 카메라 따라오기(`CameraLagSpeed 10`) 중에는 구멍 위치가 아주 조금 늦게 따라온다.
- 벽 재질 슬롯 이름 `Walls`가 바뀌면 다시 연결해야 한다(모델러 요청 사항).

## 4. 커서 기준 이동 ⟪기획 변경 2026-10-26 팀 결정⟫

### ① 기획 요구사항
- 게임_시스템.pdf 4장(“W = 월드 x축 고정, 상체만 마우스 ±90°”)을 **대체**: 캐릭터의 앞 = 항상 마우스 커서 방향. 몸 전체와 손전등이 커서를 바라봄.
- WASD는 **커서 기준**(W 앞 / S 뒤 / A 왼쪽 / D 오른쪽), 대각선도 같은 기준, 움직이는 동안에도 커서를 바라봄.
- 가정(사용자): 뒤·옆도 같은 속도(배율은 데이터), 커서 1m 안이면 마지막 방향 유지, 몸 회전은 거의 즉시.

### ② 구현 방식 — 흐름
1. `UVHAimComponent::TickComponent`: 마우스를 바닥 평면에 투영(`TraceMouseToFloor` → `DeprojectMousePositionToWorld`)한 점으로 **`AimYaw`** 계산(`VHRules::AimYawToPoint`, 데드존 100cm). 경직·숨음 등 `CanTurn()`이 거짓이면 갱신 안 함.
2. `AVHGamePlayerController::UpdateRotation`: **컨트롤 회전 = AimYaw**.
3. 캐릭터 무브먼트 `bUseControllerDesiredRotation = true`, `RotationRate = BodyTurnSpeed(1800°/s)` → 몸이 컨트롤 회전을 따라 돈다(`UVHAimComponent::ApplyRotationMode`). 손전등은 몸에 붙어 있어 같이 돈다.
4. 이동 입력: 템플릿 `AMCPTestCharacter::DoMove`가 시선 컴포넌트가 있으면 `UVHAimComponent::ComputeMoveVector` → `VHRules::AimRelativeMove`로 월드 방향을 계산해 `AddMovementInput`.

### ③ 핵심 코드
`Gameplay/VHInteractionRules.cpp` — `VHRules::AimRelativeMove`
```cpp
const FVector2D In(Forward, Right);
const float Len = In.Size();
if (Len < KINDA_SMALL_NUMBER) { return FVector::ZeroVector; }
const FVector2D D = In / Len;	// 방향만
const float Strength = FMath::Min(Len, 1.f);	// 대각선(W+A)도 세기는 1까지
const float Scale = D.X * D.X * (D.X >= 0.f ? ForwardScale : BackwardScale) + D.Y * D.Y * StrafeScale;
const FRotator YawRot(0.f, AimYaw, 0.f);
const FVector Fwd = FRotationMatrix(YawRot).GetUnitAxis(EAxis::X);
const FVector Rgt = FRotationMatrix(YawRot).GetUnitAxis(EAxis::Y);
return (Fwd * D.X + Rgt * D.Y) * (Strength * Scale);
```
- `Forward` = W(+1)/S(-1), `Right` = D(+1)/A(-1).
- 방향(D)과 세기(Strength)를 나눠서 → W+A를 같이 눌러도 길이가 1을 넘지 않는다(대각선이 더 빠르지 않음).
- 방향별 배율: 정면이면 앞 배율, 정옆이면 옆 배율, 그 사이는 cos²·sin² 비율로 섞음.
- 바라보는 각도의 앞 축(`Fwd`)·오른쪽 축(`Rgt`)으로 **2D 회전** = `앞방향×(W−S) + 오른쪽방향×(D−A)`.

`VHRules::AimYawToPoint`
```cpp
const FVector Delta(AimPoint.X - From.X, AimPoint.Y - From.Y, 0.f);
if (Delta.Size2D() <= FMath::Max(DeadZone, 1.f)) { return PreviousYaw; }
return FMath::RadiansToDegrees(FMath::Atan2(Delta.Y, Delta.X));
```
- 커서가 캐릭터 1m 안이면 방향을 바꾸지 않는다(커서가 몸 위에 있으면 작은 움직임에도 각도가 크게 튀기 때문).

`Game/VHGamePlayerController.cpp` — `AVHGamePlayerController::UpdateRotation`
```cpp
RotationInput = FRotator::ZeroRotator;
const UVHAimComponent* Aim = MyPawn ? MyPawn->FindComponentByClass<UVHAimComponent>() : nullptr;
SetControlRotation(FRotator(0.f, Aim ? Aim->GetAimYaw() : 0.f, 0.f));
```
- 템플릿의 마우스 시점 입력은 버리고(카메라 고정), 컨트롤 회전을 커서 방향으로 맞춘다.

### ④ 왜 이렇게 설계했나
- **계산을 순수 함수(`VHRules`)로 분리** → 언리얼 월드 없이 자동화 테스트(`VaultHeist.Interaction.AimMove`)로 커서 위·아래·좌·우·대각선 × W/A/S/D를 검사할 수 있다.
- 몸 회전은 엔진 기능(`bUseControllerDesiredRotation`)을 써서 직접 보간 코드를 짜지 않음.
- 기존 템플릿 캐릭터(`AMCPTestCharacter`)에는 "시선 컴포넌트가 있으면 그걸 쓴다"는 분기만 추가 → 컴포넌트 구조 유지.

### ⑤ 다른 방법과 비교
| 방법 | 장점 | 단점 |
|---|---|---|
| (채택) 커서 기준 이동 + 몸 전체 회전 | 트윈스틱 슈터처럼 직관적, 손전등 = 앞 | 화면 기준 이동에 익숙한 사람은 처음 헷갈림 |
| (이전) 월드 축 이동 + 상체만 ±90° | 기획서 원안 | 상체 애니메이션 필요, 시선 제한 구현 복잡 |
| 하체=이동, 상체=커서 분리 | 실감 | 애니메이션·블렌딩 필요(마네킹이라 불가) |

### ⑥ 한계·개선
- 상체·하체 애니메이션 없음(머리 위 원뿔로 시선 표시).
- 카메라 lag 중에는 같은 화면 위치 커서라도 바닥 점이 조금 바뀌어 방향이 몇 도 흔들릴 수 있음(보고서 확인 필요 8).
- `VHGoto` 순간이동 후엔 커서를 오브젝트 쪽에 둬야 한다(개발용 명령).
- 서버: `CS_Move.yaw`가 이제 몸 방향과 같고, 뒤·옆 이동 속도 검증을 맞춰야 함(`04`).

## 5. 구르기·달리기·스테미나·탈진

### ① 기획 요구사항 (게임_시스템.pdf 5·6·10장)
- 걷기 3m/s, 달리기 6m/s(10pt/s), 구르기 9m/s·0.5초·20pt·**무적**, 공격 30pt. 최대 100pt, 자연 회복 10pt/s.
- **탈진**: 0pt가 되면 회복 50% 감소 + 특수 동작 불가, 최대치까지 회복되면 해제.
- 팀 결정: 점프 없음, Space = 구르기.

### ② 구현 방식
`UVHActionComponent` (`Gameplay/VHActionComponent.cpp`)가 스테미나·달리기·구르기·공격과 **이동 속도(MaxWalkSpeed)** 를 매 프레임 결정. 수치는 `FVHCharacterStats`(`Gameplay/VHGameplayTypes.h`, 데이터 에셋 `DA_VHGameplayConfig.ThiefStats`).
입력: `AVHGamePlayerController`가 Shift(`IA_VHSprint`)·Space(`IA_VHRoll`)·좌클릭(`IA_VHAttack`)을 받아 `RequestRoll` 등을 부른다.

### ③ 핵심 코드
`UVHActionComponent::SpendStamina`
```cpp
Stamina = FMath::Max(0.f, Stamina - Amount);
if (Stamina <= KINDA_SMALL_NUMBER)
{
    Stamina = 0.f;
    SetExhausted(true);	// 0pt가 되면 탈진 [기획]
}
```
- 모든 소비(달리기·구르기·공격)가 이 함수 하나를 지난다 → 탈진 진입 규칙이 한 곳.

`UVHActionComponent::TickComponent` (달리기·회복·속도)
```cpp
bRunning = bWantsSprint && bHasMoveInput && bMoving && bCanAct && !bRolling && !IsAttacking() && !bInteracting
    && !bExhausted && Stamina > 0.f;
if (bRunning) { SpendStamina(Stats.RunStaminaPerSecond * GetStaminaMultiplier() * DeltaTime); … }
…
if (!bRunning && !bRolling && !IsAttacking())
{
    const float Rate = Stats.StaminaRegenPerSecond * (bExhausted ? C.ExhaustedRegenMultiplier : 1.f);
    Stamina = FMath::Min(Stats.MaxStamina, Stamina + Rate * DeltaTime);
    if (bExhausted && Stamina >= Stats.MaxStamina - KINDA_SMALL_NUMBER) { SetExhausted(false); }
}
…
CurrentMaxSpeed = (bRunning ? Stats.RunSpeed : Stats.WalkSpeed) * GetSpeedMultiplier();
```
- 달리기는 "Shift + 실제 이동 입력 + 실제로 움직이는 중 + 행동 가능 + 탈진 아님"일 때만. 매 프레임 `초당 소비 × 무게 배율 × 프레임 시간`만큼 깎는다.
- 특수 동작 중이 아니면 회복. 탈진이면 `ExhaustedRegenMultiplier`(0.5) → 초당 5. **100까지 차야** 해제.
- 최대 속도 = 걷기/달리기 × 무게 감속(6장). 구르는 중에는 `RollSpeed`(감속 없음).

`UVHActionComponent::RequestRoll` (일부)
```cpp
FVector Dir = Pawn ? Pawn->GetLastMovementInputVector() : FVector::ZeroVector;
…
if (Dir.SizeSquared() < 0.01f) { … Dir = Aim ? FRotator(0.f, Aim->GetAimYaw(), 0.f).Vector() : …; }
…
Status->SetInvulnerable(true);	// 구르는 중 무적 [기획]
SetMoveInputBlocked(true);			// 구르는 동안 방향을 바꾸지 않는다
Movement->MaxAcceleration = 100000.f;	// 바로 9m/s가 되게
Movement->Velocity = RollDirection * Stats.RollSpeed;
```
- 방향 = 지금 누른 이동 키 방향(이미 커서 기준으로 계산된 월드 방향), 없으면 커서 쪽.
- 무적 플래그(`UVHStatusEffectComponent`) → 이 동안 경직 안 됨(`CanBeStunned`).
- 0.5초 동안 Tick에서 `AddMovementInput(RollDirection, 1.f, true)`로 계속 밀고, 끝나면 `EndRoll`.
- 구르는 애니메이션이 없어 메시를 Z 0.55배로 눌러 "웅크림"을 표시(임시).

### ④ 왜 이렇게 설계했나
- 스테미나·속도·동작 상태가 서로 얽혀 있어(달리는 중엔 회복 안 함, 공격 중엔 구르기 안 함 …) **한 컴포넌트가 한 Tick에서** 결정하게 했다 → 순서 문제(누가 먼저 속도를 바꾸나)가 없다.
- 캐릭터 클래스 대신 컴포넌트 → 진짜 캐릭터가 정해지면 컴포넌트만 붙이면 된다.

### ⑤ 다른 방법과 비교
| 방법 | 장점 | 단점 |
|---|---|---|
| (채택) 액터 컴포넌트 + Tick | 단순, C++로 한 곳 | 상태가 늘면 함수가 길어짐 |
| Gameplay Ability System(GAS) | 쿨다운·비용·태그 체계 완비 | 학습량 큼, 서버 판정 구조가 우리 서버와 다름 |
| 애니메이션 몽타주로 구르기 | 실제 동작 | 애니메이션 없음(마네킹) |

### ⑥ 한계·개선
- 스테미나가 모자라도 0까지 쓰고 동작 실행(가정, 확인 필요).
- 구르기 거리 실측 약 4.5m(0.5초 × 9m/s), 벽에 부딪히면 그 자리에서 멈춤.
- 경비원(NPC)은 스테미나 미사용(기획) — 경비원 AI 미구현.

## 6. 무게와 소지 한도

### ① 기획 요구사항
- 최대 무게 20kg, 소지 10개(게임_시스템.pdf 3장). **임시 규칙(사용자 결정 2026-10-25)**: 20kg을 넘게 되면 못 주움, 속도는 무게에 비례(0kg 0% → 20kg 50% 감소), 특수 동작 스테미나 ×1 → ×2, 구르기 속도는 제외.

### ② 구현 방식
- 소지: `UVHTreasureCarrierComponent`(`Items` 배열, `GetTotalWeight`, `GetTotalValue`, `CanAccept`).
- 규칙: 순수 함수 `VHRules::CheckPickup`, `WeightRatio`, `SpeedMultiplier`, `StaminaCostMultiplier` (`Gameplay/VHInteractionRules.cpp`).
- 적용: `UVHActionComponent::GetSpeedMultiplier / GetStaminaMultiplier` → 5장의 속도·소비 계산. 줍기 전에 판정 담당이 `CheckCarry`로 막고 이유 문구를 보여준다.

### ③ 핵심 코드
`VHRules::CheckPickup`
```cpp
if (MaxCount > 0 && CurrentCount >= MaxCount) { return EVHInteractBlock::TreasureFull; }
if (MaxWeight > 0.f && CurrentWeight + ItemWeight > MaxWeight + KINDA_SMALL_NUMBER) { return EVHInteractBlock::TooHeavy; }
return EVHInteractBlock::None;
```
- 개수 한도를 먼저, 그다음 "**지금 무게 + 새 보물 > 20kg**"이면 거절. 딱 20kg은 허용(테스트 `CarryRules`로 확인). 한도 0 = 제한 없음(더미 경비원은 `bUnlimited`).

```cpp
float VHRules::SpeedMultiplier(float InWeightRatio, float MaxPenalty)
{ return FMath::Clamp(1.f - MaxPenalty * FMath::Clamp(InWeightRatio, 0.f, 1.f), 0.f, 1.f); }
float VHRules::StaminaCostMultiplier(float InWeightRatio, float MaxMultiplier)
{ return 1.f + (FMath::Max(MaxMultiplier, 1.f) - 1.f) * FMath::Clamp(InWeightRatio, 0.f, 1.f); }
```
- 무게 비율 = 무게 ÷ 20kg. 속도 = 1 − 0.5 × 비율, 스테미나 배율 = 1 + 1 × 비율. 예) 10kg → 속도 75%, 스테미나 ×1.5.

### ④ 왜 이렇게 설계했나
- "딱 20kg에서만 50% 감소" 같은 계단식보다 **비례**가 자연스럽다는 사용자 결정. 공식이 단순한 순수 함수라 테스트하기 쉽다.
- 보물마다 무게·가치가 다르므로 개수(`int`)가 아니라 **아이템 목록(`FVHItemData` 배열)** 으로 들고 다닌다. 의자·그림·책·꽃병도 같은 구조로 넣을 수 있게 `EVHItemKind`를 준비(팀 결정).

### ⑤ 다른 방법과 비교
- 계단식(무게 초과 시 고정 감속): 구현 쉬움, 갑자기 느려져 어색.
- 곡선(제곱 등): 더 섬세, 기획 근거 없음 → 확인 필요로 남김.

### ⑥ 한계·개선
- 전부 **임시 규칙**(기획 확정 전). 퍽으로 한도 변경은 미구현(`FVHCharacterStats`를 퍽이 복사·수정하는 구조만 준비).

## 7. 소리 시스템

### ① 기획 요구사항 (게임_시스템.pdf 8장)
| 동작 | 반경 | 신호 간격 |
|---|---|---|
| 걷기 | 0m | 0.5초 |
| 달리기 | 12m | 0.2초 |
| 구르기 | 15m | 동작 끝날 때까지 |
| 공격 빗나감 / 적중 | 5m / 20m | 1번 |
| 보물 소지 | 개당 +2m, 최종 ×1.1 | – |
- 벽과 상관없이 구 형태로 들린다. 경비원은 마지막으로 들은 소리 위치로 걸어간다(경비원 AI는 미구현).

### ② 구현 방식
`UVHMovementNoiseComponent` (`Gameplay/VHMovementNoiseComponent.cpp`)가 매 Tick 지금 동작(정지/걷기/달리기/구르기)을 판단 → 반경 계산(`VHRules::NoiseRadius`) → 간격마다 `EmitSignal` → `UVHInteractionSubsystem::ReportNoise` / `OnNoise` 델리게이트(경비원 AI가 들을 자리). 공격 소리는 `EmitOneShot`. 바닥에 원을 그려 눈으로 확인(`VHShowNoise`).

### ③ 핵심 코드
`VHRules::NoiseRadius`
```cpp
if (TreasureCount <= 0) { return FMath::Max(0.f, BaseRadius); }
return FMath::Max(0.f, (BaseRadius + PerTreasure * TreasureCount) * Multiplier);
```
- (동작 반경 + 2m × 보물 수) × 1.1. 예) 보물 2개 들고 달리기 = (12 + 4) × 1.1 = 17.6m.

`UVHMovementNoiseComponent::TickComponent` (일부)
```cpp
const bool bSilent = State && (State->GetStatus() == EVHThiefStatus::Hidden || !State->IsInGame());
…
NoiseRadius = bSilent ? 0.f : VHRules::NoiseRadius(Base, NoisyTreasure, C.NoisePerTreasure, C.TreasureNoiseMultiplier);
…
else if (MoveState != OldState || Now >= NextSignalTime)
{
    EmitSignal(NoiseRadius, EVHNoiseKind::Move);
    NextSignalTime = Now + GetSignalInterval();
}
```
- 숨은 동안·탈출 후에는 0. 동작이 바뀌면 즉시 1번, 그 뒤 간격(걷기 0.5 / 달리기 0.2 / 구르기 0 = 매 프레임)마다 신호.
- "신호 간격"은 실제 소리 재생 간격이 아니라 **경비원이 감지할 수 있게 위치를 알리는 간격**이다(기획 문구).

### ④ 왜 이렇게 설계했나
- 소리를 **이벤트(위치·반경·종류)** 로 만들어 보내기만 하고, 듣는 쪽(경비원 AI)은 나중에 구독 → 서로 모른다(느슨한 결합). 서버 판정이 되면 같은 이벤트를 패킷으로 바꾸면 된다.

### ⑤ 다른 방법과 비교
- 언리얼 AI Perception(Hearing): 엔진 기능 활용, 대신 "벽 무시·간격" 같은 기획 규칙을 맞추려면 설정이 복잡하고 서버 판정과 이중화.
- 매 프레임 신호: 정확하지만 패킷·연산 많음 → 기획의 간격 방식 채택.

### ⑥ 한계·개선
- **듣는 쪽(경비원 AI) 미구현**. 서 있을 때도 보물 소리를 낸다(`bTreasureNoiseWhileStill = true`, 제안값 — 확인 필요).
- 서버 프로토콜 v2에서는 `SC_NOISE`가 삭제됐고, 서버 `GAME_SYSTEM.md`에는 "발소리"를 서버가 처리하는 것으로 나온다 → 소리 계산을 서버가 할지 클라이언트가 할지 서버 팀원과 맞춰야 함(`04` 참고, 확인 필요).

## 8. 상호작용 공통 시스템

### ① 기획 요구사항
- 반경 1.5m 안, 시선(커서) 방향의 오브젝트 하나가 대상. **짧게 누르기(Tap)** / **길게 누르기(Hold)**. 금고는 떼도 진행도 유지, 창고 문은 처음부터. **동시 1명**.
- 팀·사용자 결정: 상호작용 가능한 물품은 **손전등 빛 안에서만 색 테두리**, 상호작용도 빛 안에서만(예외: 반납지점은 항상, 숨은 상태의 "나오기", 길게 누르기 시작 후 빛이 벗어나도 계속).

### ② 구현 방식 — 역할 분리 (한 줄 요약: **컴포넌트는 입력·표시, 판정은 한 곳, 반영은 한 입구**)
```
키 입력 → AVHGamePlayerController → UVHInteractionComponent(대상 찾기·입력)
              │ RequestBegin / RequestCancel
              ▼
   UVHInteractionAuthority (판정 — 지금은 UVHLocalInteractionAuthority, 클라이언트 판정)
              │ Evaluate / BuildOffer / ResolveComplete
              ▼
   UVHInteractionSubsystem::Apply*  (결과를 화면·상태에 반영하는 입구)
              ▼
   오브젝트 액터(AVHInteractableBase 자식: Safe, HideSpot …) / 컴포넌트 / HUD
```
| 파일 | 내용 |
|---|---|
| `Gameplay/VHInteractionComponent.cpp` | 매 Tick: 빛 안 물품 집합 → `UpdateFocus`(대상) → `UpdateOutlines`(테두리). `InteractPressed/Released`, `NotifyMoveInput` |
| `Gameplay/VHInteractionAuthority.cpp` | `BuildOffer`(오브젝트별 규칙), `Evaluate`(공통 규칙·1명 제한), `RequestBegin`(세션 시작), `Tick`(완료·중단), `ResolveComplete`(끝났을 때 일) |
| `Gameplay/VHInteractionSubsystem.cpp` | `ApplyInteract`, `ApplySafeOpened`, `ApplyHide` … (월드 서브시스템) |
| `Gameplay/VHInteractionRules.cpp` | `FVHHoldProgress`(진행도), `TargetScore` |
| `Gameplay/VHFlashlightComponent.cpp` | `IsBoxLit` — 빛 안 판정 |
| `Gameplay/VHInteractableBase.cpp` | `SetOutline` — 커스텀 스텐실 |

### ③ 핵심 코드
**(a) 빛 안 물품 → 대상 찾기** — `UVHInteractionComponent::TickComponent`
```cpp
for (AVHInteractableBase* T : Sub->GetInteractables())
{
    if (T->IsAlwaysVisible() || (Light && Light->IsBoxLit(T->GetInteractBounds(), T)))
    { Visible.Add(T); }
}
if (IsInteracting()) { FocusOffer = Sub->GetAuthority()->Evaluate(this, ActiveTarget.Get()); }
else { UpdateFocus(Visible); }
UpdateOutlines(Visible);
```
- 반납지점(`IsAlwaysVisible`)은 항상, 나머지는 손전등 빛 안일 때만 "보이는 물품".
- **진행 중에는 대상을 고정**(빛이 벗어나도 취소 안 함 — 사용자 결정).

`UVHFlashlightComponent::IsBoxLit`
```cpp
if (FVector::DotProduct(Dir, To / Dist) < CosCone) { continue;	// 원뿔 밖 }
FHitResult Hit;
if (!World->LineTraceSingleByChannel(Hit, Origin, P, ECC_Visibility, Params)) { return true;	// 가려지지 않음 }
```
- 물품 상자의 대표점 6개(가운데·윗면·좌우앞뒤) 중 하나라도 ① 거리 안(1800cm), ② **원뿔 각도 안**(내적 ≥ cos 28°), ③ 벽에 안 가리면(라인 트레이스) 빛 안.

`UVHInteractionComponent::UpdateFocus` (점수)
```cpp
const float Distance = FVector::Dist2D(Closest, Location);
if (Distance > C.SearchRadius) { continue; }
…
const float Score = VHRules::TargetScore(Distance, AngleDeg, C.SearchRadius, C.MaxFacingAngle);
```
`VHRules::TargetScore`
```cpp
if (Radius <= 0.f || Distance > Radius) { return -1.f; }
if (Distance > KINDA_SMALL_NUMBER && AngleDeg > MaxAngleDeg) { return -1.f; }
const float AnglePart = Distance > KINDA_SMALL_NUMBER && MaxAngleDeg > 0.f ? AngleDeg / MaxAngleDeg : 0.f;
return Distance / Radius + AnglePart;
```
- 거리(상자 가장자리까지, 수평)와 시선과의 각도를 각각 0~1로 맞춰 더한 **점수가 가장 작은** 것 하나. 1.5m 밖·75° 밖은 제외. 탑뷰라 시선 레이캐스트 대신 점수 방식.

**(b) 짧게/길게, 진행도 유지** — `UVHLocalInteractionAuthority::BuildOffer` (금고)
```cpp
case EVHSafeState::Closed:
    // [기획] 길게 누르기 30초, 진행도 유지
    return FVHInteractOffer::Make(EVHInteractMode::Hold, C.SafeOpenSeconds * Scale, C.bSafeKeepProgress, C.SafeOpenText);
```
- "Offer" = 이 대상과 지금 할 수 있는 일(방식 Tap/Hold, 시간, 취소 시 진행도 유지 여부, 문구, 막힌 이유). 오브젝트 종류별 규칙이 **이 switch 한 곳**에 모여 있다. `Scale`은 개발용 `VHFastInteract` 배율.

`FVHHoldProgress` (`VHInteractionRules.cpp`)
```cpp
float FVHHoldProgress::GetProgress(double Now) const
{
    if (!bRunning) { return SavedProgress; }
    const float Elapsed = static_cast<float>(FMath::Max(0.0, Now - StartTime));
    return FMath::Clamp(SavedProgress + Elapsed / TotalSeconds, 0.f, 1.f);
}
void FVHHoldProgress::Cancel(double Now, bool bKeep) { SavedProgress = bKeep ? GetProgress(Now) : 0.f; bRunning = false; }
```
- 진행도를 **초가 아니라 비율(0~1)** 로 저장. 시작 시각 + 경과/전체로 계산하므로 매 프레임 더하지 않는다(서버가 주는 "시작 시각·남은 시간"으로 복원 가능 — `BeginWithRemaining`).
- 취소 시 금고는 비율 유지, 창고 문은 0으로.

`UVHInteractionComponent::InteractReleased / NotifyMoveInput`
```cpp
if (IsInteracting() && ActiveMode == EVHInteractMode::Hold)
{ … Sub->GetAuthority()->RequestCancel(this); }
```
- 길게 누르기만 키를 떼거나 **이동 키·Space·좌클릭**(`NotifyActionInput`)이면 취소. 짧게 누르기는 끝까지 진행.

**(c) 동시 1명** — `UVHLocalInteractionAuthority::Evaluate`
```cpp
const UVHInteractionComponent* User = Target->GetActiveUser();
if (User && User != By)
{ return Offer.Blocked(EVHInteractBlock::Busy, LOCTEXT("Busy", "다른 의적이 사용 중입니다")); }
```
- 같은 함수에서 숨은 상태·잡힘·갇힘·경직이면 막는다(숨은 곳의 "나오기"만 예외).

**(d) 진행 중 감시** — `UVHLocalInteractionAuthority::Tick`
```cpp
const FVHInteractOffer Now_Offer = Evaluate(S.By.Get(), S.Target.Get());
if (!Now_Offer.IsAvailable() || Now_Offer.Mode != S.Offer.Mode) { CancelSession(i, …); continue; }
if (Now >= S.StartTime + S.Duration) { CompleteSession(i); }
```
- 매 프레임 "아직 할 수 있나"를 다시 판정(잡힘·경직·대상 상태 변화 → 즉시 취소), 시간이 다 되면 완료 → `ResolveComplete`가 오브젝트별 결과를 `Apply*`로 반영.

**(e) 테두리(커스텀 스텐실 외곽선)** — `AVHInteractableBase::SetOutline`
```cpp
const bool bOn = State != EVHOutline::None;
const int32 Stencil = static_cast<int32>(State);
ForEachComponent<UMeshComponent>(false, [bOn, Stencil](UMeshComponent* Mesh)
{
    if (Mesh->IsVisible()) { Mesh->SetRenderCustomDepth(bOn); Mesh->SetCustomDepthStencilValue(Stencil); }
```
- 물품 메시를 **커스텀 뎁스 버퍼**에 그리게 하고, **스텐실 값**으로 상태를 적는다: 1 = 빛 안(옅은 노랑), 2 = 현재 대상(주황), 3 = 대상이지만 지금 불가(회색) (`EVHOutline`, `Gameplay/VHInteractionTypes.h`).
- 화면 후처리 재질 `M_VHOutline`(`AVHGamePlayerController::ApplyOutlinePostProcess`가 카메라 블렌더블에 추가, `r.CustomDepth=3` 필요)의 Custom 노드가 픽셀마다 주변 8방향의 스텐실을 보고, **자기는 0인데 이웃이 0이 아니면 가장자리**로 판단해 그 값의 색을 칠한다(그래프의 HLSL: `SceneTextureLookup(…, 25, …)` = CustomStencil, `edge = (c < 0.5 && m > 0.5)`, `m > 2.5`면 회색·`m > 1.5`면 주황). 이 코드는 에셋 그래프 안에 있다(2026-10-26 에디터에서 Custom 노드 코드를 읽어 이 인용과 같음을 확인).

### ④ 왜 이렇게 설계했나
- **나중에 서버가 판정**하게 될 것을 전제로 "판정(Authority)"과 "반영(Apply*)"을 나눴다. 서버판으로 바꿀 때는 `UVHInteractionAuthority`를 상속한 클래스가 `RequestBegin` → `C_ACTION` 전송, 받은 SC_ 패킷 → 같은 `Apply*` 호출만 하면 된다(헤더 주석에 명시). 오브젝트·HUD는 그대로.
- 진행도를 비율로 → 기획이 30초를 40초로 바꿔도 진행도가 자연스럽고, 서버 시각으로 다시 계산 가능.
- 외곽선을 포스트 프로세스로 → 메시마다 재질을 바꾸지 않고 모양 그대로 테두리(이전 "반투명 발광" 방식은 기본 도형에서 면 전체가 칠해지는 문제 — 10-23 보고서 남은 문제였음).

### ⑤ 다른 방법과 비교
| 주제 | 채택 | 대안 |
|---|---|---|
| 대상 선택 | 거리+각도 점수 | 화면 중앙 레이캐스트(1·3인칭용, 탑뷰엔 부적합) / 오버랩 박스(가장 가까운 것만) |
| 판정 위치 | 판정 담당 클래스 하나(교체 가능) | 오브젝트마다 Interact() 가상함수(간단하지만 서버 판정으로 바꾸기 어려움) |
| 테두리 | 커스텀 스텐실 + 후처리 | 메시 위에 반투명 재질 덧씌우기(이전 방식) / 메시 두 번 그리기(역면) |

### ⑥ 한계·개선
- 진행 바는 원형이 아니라 가로 막대(UI 미정). 안내 문구의 `[우클릭/G]`가 코드에 고정.
- 판정이 **클라이언트에 있다**(치트 가능) — 서버 판정으로 교체 예정(`04`).
- 손전등 빛 판정은 대표점 6개라 아주 큰 물품의 일부만 비출 때 놓칠 수 있다.

## 9. 금고·보물·반납지점·탈출구·숨는 곳·창고

### ① 기획 요구사항
- **금고**: 길게 30초, 진행도 유지, 열리면 보물 1개(짧게). 팀 결정: **보물은 금고에서만, 금고마다 다른 가치**. 기획: **10곳 중 매 판 5곳 랜덤 등장**.
- **반납지점**(PDF 2장): 방마다 랜덤 바닥에 1m 초록 사각형, 50초 빨강, 60초 사라짐, **항상 5곳**, 반납·만료 시 사라진 방을 뺀 다른 방에 즉시 새로. 반납 가치 **10,000$** 달성 → 전체 메시지 + 탈출구 열림.
- **탈출구**(팀 결정): 들어가면 자동 탈출(상호작용 없음). 제한 시간 5분.
- **숨는 곳**: 1곳 1명, 들어가기 1초·나오기 0.5초. **창고**: 길게 5초, 떼면 처음부터, 갇힌 의적 전원 구출.

### ② 구현 방식
| 오브젝트 | 액터 | 규칙·반영 |
|---|---|---|
| 금고 | `AVHSafe` (`EVHSafeState`: Closed/Opened/Empty) | Offer: `BuildOffer` / 반영: `ApplySafeOpened`, `ApplySafeTreasureTaken` / 배정: `UVHInteractionSubsystem::AssignSafeTreasures` |
| 떨어진 보물 | `AVHDroppedTreasure` | 경직 때만 생김(`DropItemsAround` → `SpawnDroppedTreasure`) |
| 반납지점 | `AVHReturnPoint` | `UVHMatchSubsystem::SpawnReturnPoint / ReplaceReturnPoint / ApplyReturned / Tick` |
| 탈출구 | `AVHExitGate` | `UVHMatchSubsystem::CheckExitUnlock / UnlockExit / HandleEscapeZone`, `AVHExitGate::HandleEscapeZoneOverlap` |
| 숨는 곳 | `AVHHideSpot` | `ApplyHide` (탑뷰에서는 숨는 곳 카메라 끔: `bUseHideCamera = false`) |
| 창고 | `AVHJailDoor` | `ApplyJail`, `ApplyRescue` (프로토콜에 아직 없어 클라이언트 전용) |
| 한 판 규칙 | `UVHMatchSubsystem` (월드 서브시스템) | 반납 가치 합계, 제한 시간, 게임 끝 → `EndMatch` → `SendResultReport` → `UVHNetSubsystem::ReportLocalMatchEnd` |

### ④ 왜 이렇게 설계했나
- **한 판 규칙(가치·반납지점·시간·탈출)** 은 상호작용과 별개라 `UVHMatchSubsystem`으로 분리 → 상호작용 서브시스템이 비대해지지 않는다. 둘 다 **월드 서브시스템**이라 레벨마다 새로 만들어지고 레벨이 끝나면 사라진다(한 판의 수명과 같음).
- 금고·반납지점·탈출구 위치는 모두 **레벨에 놓인 액터**라 기획자가 끌어서 옮길 수 있다.

### ⑤ 다른 방법과 비교
- 반납지점을 레벨에 미리 여러 개 놓고 켜고 끄기: 위치 통제 쉬움, 대신 "방 안 랜덤 바닥" 기획과 다름 → 방 영역 + 무작위 바닥 채택.
- 탈출을 상호작용(키)으로: 이전 방식(10-23). 팀 결정으로 자동 탈출로 바꿈.

### ⑥ 한계·개선
- 반납하지 않고 들고 탈출한 보물은 가치에 안 들어감(가정). 결과의 "탈출시킨 보물" = 반납 수(가정).
- 창고 구출·잡힘은 프로토콜에 없어 **클라이언트 전용**(서버 요청 목록).
- 숨는 곳 카메라(옷장 밖 카메라) 기능은 남아 있지만 탑뷰에서는 끔.
- 판정이 모두 클라이언트(`UVHLocalInteractionAuthority`, `UVHMatchSubsystem`) — 서버 판정으로 이동 필요.

## 10. 공격과 경직

### ① 기획 요구사항 (PDF 7·10장)
- 공격 1초(선 딜레이 20% / 판정 50% / 후 딜레이 30%), 30pt, **시선 방향 120° 부채꼴**, 범위 "신체 비례"(임시 1.5m).
- 의적 → 경비원: **경직 3초**, 이후 **10초 면역**. 의적 → 의적: 효과 없음. 구르는 중(무적): 효과 없음.
- 경직: 이동·스킬 불가, **보유 보물 전부 떨어뜨림**(다시 주울 수 있음 — 팀 결정). 공격 중 이동 가능(사용자 결정).

### ② 구현 방식
`UVHActionComponent::RequestAttack` → 매 Tick `UpdateAttack`(구간 판정) → 판정 구간에 `SweepAttack`(전투 대상 목록을 돌며 `VHRules::IsInAttackFan`) → 맞으면 판정 담당 `ResolveAttackHit` → `UVHInteractionSubsystem::ApplyStun` → `UVHStatusEffectComponent::ApplyStun` + `DropItemsAround`.

### ③ 핵심 코드
`UVHActionComponent::UpdateAttack`
```cpp
const float T = static_cast<float>((Now - AttackStartTime) / Duration);
const float ActiveStart = C.AttackWindupRatio;                      // 0.2
const float ActiveEnd = C.AttackWindupRatio + C.AttackActiveRatio;  // 0.7
if (T < ActiveStart) { AttackPhase = EVHAttackPhase::Windup; }
else if (T < ActiveEnd) { AttackPhase = EVHAttackPhase::Active; }
else if (T < 1.f) { AttackPhase = EVHAttackPhase::Recovery; }
else { EndAttack(); return; }
```
- 경과 비율로 세 구간(작은 상태 머신). 판정 구간(0.2~0.7초) 동안 매 프레임 `SweepAttack`, 한 대상은 한 번만(`AttackHits`).

`VHRules::IsInAttackFan`
```cpp
if (Distance > Radius + TargetRadius) { return false; }
if (Distance <= TargetRadius) { return true;	// 몸이 겹칠 만큼 가까우면 방향과 상관없이 적중 }
const FVector Forward = FRotator(0.f, AttackYaw, 0.f).Vector();
const float Angle = FMath::RadiansToDegrees(FMath::Acos(FMath::Clamp(FVector::DotProduct(Forward, To / Distance), -1.f, 1.f)));
const float Slack = FMath::RadiansToDegrees(FMath::Atan2(TargetRadius, Distance));
return Angle <= FullAngleDeg * 0.5f + Slack;
```
- 거리 ≤ 1.5m + 상대 몸 반지름, 그리고 공격 방향과의 각도 ≤ 60°(120°의 절반) + 몸 반지름만큼의 여유각. **내적 → acos**로 각도를 구한다.

`UVHLocalInteractionAuthority::ResolveAttackHit`
```cpp
if (Target->Kind != EVHEntityKind::Guard) { return EVHAttackOutcome::NoEffect; }
if (Target->IsInvulnerable()) { return EVHAttackOutcome::Invulnerable; }
if (!Sub->ApplyStun(Target, G.StunSeconds, G.StunImmunitySeconds)) { return EVHAttackOutcome::Immune; }
```
`UVHInteractionSubsystem::ApplyStun`
```cpp
if (!Status || !Status->CanBeStunned()) { return false; }
if (Authority) { Authority->NotifyActorStunned(Owner); }   // 하던 상호작용 즉시 취소
Status->ApplyStun(Seconds, ImmunitySeconds);
if (UVHTreasureCarrierComponent* Carrier = Owner->FindComponentByClass<UVHTreasureCarrierComponent>())
{ Dropped = DropItemsAround(Owner, Carrier->ApplyRemoveAll()); }
```
- `CanBeStunned` = 경직 중 아님 && 면역 아님 && 무적 아님. 경직되면 입력 차단(`SetIgnoreMoveInput`), 보물을 반경 1.3m(`DropScatterRadius`) 원 위에 `AVHDroppedTreasure`로 뿌린다(이름·무게·가치 유지).
- 소리: 판정 구간이 끝날 때까지 경비원을 못 맞히면 빗나감 5m, 맞히면 20m 한 번(`EmitOneShot`).

### ④ 왜 이렇게 설계했나
- "공격이 닿았는지(기하)"는 순수 함수로, "닿으면 무슨 일이 생기나(규칙)"는 판정 담당으로 → 기하는 테스트, 규칙은 서버로 옮기기 쉬움.
- 경직·면역·무적을 `UVHStatusEffectComponent` 하나에 → 의적·경비원이 같은 컴포넌트를 쓴다.

### ⑤ 다른 방법과 비교
- 충돌 콜리전(무기 메시 오버랩): 애니메이션과 맞물려 정확, 대신 애니메이션 필요·서버와 판정이 달라질 수 있음 → 기획의 "부채꼴" 수식 채택.
- 즉시 판정(누른 순간 1번): 단순, 선/후 딜레이 기획과 다름.

### ⑥ 한계·개선
- 공격 범위 1.5m는 임시("신체 비례"). 면역 중 경비원을 때려도 "적중" 소리(제안, 확인 필요).
- 경비원은 움직이지 않는 **더미**(`AVHDummyGuard`) — 경비원이 의적을 공격·체포하는 AI는 미구현(`VHCapture` 콘솔로 대신).

## 11. 맵 가져오기와 방 나누기

### ① 기획 요구사항
- 모델러의 저택 1층 블록아웃(`Art/Map/Mansion_1F_Blockout.fbx`, Blender cm 1:1, 약 98m × 69m, 벽 3m, 충돌 박스 98개 `CollisionBox000~097` — `UCX_` 이름 아님), 나중에 맵이 바뀌면 쉽게 교체.
- 반납지점이 쓰는 "방(지역)"을 방마다 만들기(복도 제외).

### ② 구현 방식 (에셋 작업 — C++ 변경은 거의 없음)
1. MCP `import_file`로 가져옴 → `Content/VaultHeist/Maps/Mansion/SM_Mansion_1F`(삼각형 1,176개, 재질 슬롯 `Floor`·`Walls`). 충돌 박스는 메시 안의 **보이지 않는 볼록 충돌 요소 98개**로 들어옴.
2. 사용자 결정 (가): 콜리전 복잡도 = **복합 콜리전을 단순 콜리전으로 사용**(`CTF_UseComplexAsSimple`) → 보이는 벽·바닥 메시가 곧 충돌.
3. 레벨 `L_Mansion_1F`: `L_InteractionTest`를 복제해 조명·후처리·게임 모드 재사용, 맵 액터를 **Z -90°** 회전(평면도 위 = 화면 위). 결과: **언리얼 X = 평면도 Y × 100, 언리얼 Y = 평면도 X × 100**. 뒤집힘 없음(위에서 찍어 확인).
4. 내비 메시: `NavMeshBounds_Mansion` → `RecastNavMesh`(정적).
5. 방 나누기: 벽 상자 98개 좌표를 평면도 좌표로 변환해 표로 만든 뒤 방 33곳을 `AVHRoomVolume`(`Gameplay/VHRoomVolume.h`)으로 배치. **문 없는 방 3곳(11·13·20)** 은 `bAllowReturnPoint = false`. 그림 `Docs/Mansion_1F_지역.png`(도구 `Tools/MapOverlay/draw_overlay.ps1` + `rooms.csv`).
6. 게임 레벨 연결: `Config/DefaultGame.ini`의 `GameLevel=` 한 줄.

### ③ 핵심 코드
`Gameplay/VHRoomVolume.cpp` — `AVHRoomVolume::FindRandomFloorPoint`
```cpp
const FVector Top(FMath::FRandRange(MinX, MaxX), FMath::FRandRange(MinY, MaxY), Box.Max.Z);
FHitResult Hit;
if (!World->LineTraceSingleByChannel(Hit, Top, Top - FVector(0.f, 0.f, Box.GetSize().Z + 400.f), ECC_Visibility, Params)) { continue; }
if (Hit.ImpactNormal.Z < 0.8f || Hit.ImpactPoint.Z > Box.Min.Z + 60.f) { continue;	// 바닥이 아니다 }
const FVector Probe = Hit.ImpactPoint + FVector(0.f, 0.f, 100.f);
if (World->OverlapAnyTestByObjectType(Probe, FQuat::Identity, Blockers, FCollisionShape::MakeBox(…), Params)) { continue; }
```
- 방 상자 안 무작위 위치에서 아래로 쏴 바닥을 찾고(법선이 위를 보고 낮은 곳), 그 자리에 1m 상자를 놓아 아무것도 겹치지 않으면 OK(최대 40번 시도). 벽 메시가 충돌을 가지므로 이 검사가 그대로 동작한다.

`Network/VHSettings.cpp` / `Config/DefaultGame.ini`
```ini
GameLevel=/Game/VaultHeist/Maps/Mansion/L_Mansion_1F.L_Mansion_1F
```
- 메뉴에서 들어갈 게임 레벨. 테스트 레벨로 돌아가려면 이 줄만 바꾸고 에디터를 다시 연다.

### ④ 왜 이렇게 설계했나
- **맵 메시(모델러 담당)와 게임 오브젝트(기획 담당)를 다른 액터로 분리** → 새 FBX를 덮어쓰고 [메시 리임포트] 하면 배치는 그대로(실제로 리임포트해 충돌 설정·재질 유지 확인). 절차는 `Docs/맵_교체_가이드.md`.
- 충돌 (가)를 고른 이유(사용자 선택): 보이는 벽과 충돌이 항상 일치, 리임포트해도 설정 유지. (나) 박스를 숨긴 액터로 98개 배치는 맵이 바뀔 때마다 다시 배치해야 해서 교체가 가장 번거로움, (다) `UCX_`로 다시 받기는 가장 깔끔하지만 기다려야 함.

### ⑤ 다른 방법과 비교
| 방법 | 장점 | 단점 |
|---|---|---|
| (채택) 복합 콜리전을 단순으로 | 정확, 교체 쉬움 | 삼각형 충돌이라 박스보다 연산이 조금 많음(블록아웃 규모라 무시 가능) |
| UCX_ 박스 | 엔진 표준, 가벼움 | 모델러 수정 필요 |
| 방을 자동으로 찾기(바닥 영역 분할) | 맵 교체 시 자동 | 구현 복잡, 복도/방 구분이 어려움 → 수동 표 + 그림 검증 채택 |

### ⑥ 한계·개선
- 문 없는 방 3곳, 정문 바깥 바닥 없음(→ `InvisibleWall_FrontDoor`로 막음), 방 이름 미정 — 모델러 요청 사항(10-26 보고서 6장).
- 방 14번(L자)은 지역 상자가 넓은 쪽만 덮는다.
- 숨긴 금고 5개도 정적 내비 메시에 장애물로 남는다(경비원 AI 때 동적 내비 검토).
- 서버 저장소의 `Data/Maps/mansion_1f_server.json`(서버용 맵 데이터)은 같은 블록아웃이지만 **회전 없는 좌표**(x 0~9788)라서, -90° 돌린 우리 `L_Mansion_1F` 좌표와 다르다. 어느 쪽을 맞출지 팀이 정해야 한다(`04` 참고, 확인 필요).

## 12. 데이터 에셋으로 수치를 분리한 이유

### ① 요구사항
- 사용자: "숫자는 전부 데이터 에셋으로". CLAUDE.md: 핵심 로직은 C++, 조립·수치 조정은 블루프린트/에셋.

### ② 구현 방식
| 에셋 | C++ 클래스 | 담는 것 |
|---|---|---|
| `DA_VHGameplayConfig` | `UVHGameplayConfig` (`Gameplay/VHGameplayConfig.h`) | 카메라·벽 투명·시선/이동 배율·능력치(`ThiefStats`)·경직·공격·금고 보물 표·제한 시간·목표·반납지점·외곽선 색 |
| `DA_VHInteractionConfig` | `UVHInteractionConfig` | 상호작용 거리·각도·시간, 소리 반경·간격, 손전등, 구출·숨기 시간 |
| `DA_VHGameData` | `UVHGameData` | 캐릭터·퍽·맵·난이도 표시 데이터(임시) |
| `DA_VHUIStyle` | `UVHUIStyle` | UI 색·글자 크기 |

어디서든 `UVHSettings::Get().GetGameplayConfig()`로 읽는다. 에셋 경로는 `Config/DefaultGame.ini`의 `[/Script/MCPTest.VHSettings]`.

### ③ 핵심 코드 — `Network/VHSettings.cpp`
```cpp
const UVHGameplayConfig& UVHSettings::GetGameplayConfig() const
{
    if (const UVHGameplayConfig* Config = GameplayConfig.LoadSynchronous()) { return *Config; }
    return *GetDefault<UVHGameplayConfig>();
}
```
- 소프트 참조(`TSoftObjectPtr`)로 에셋을 불러오고, 없으면 **C++ 기본값(CDO)** 으로 동작 → 에셋이 깨져도 게임은 돈다. 자동화 테스트도 같은 기본값을 쓴다.

### ④ 왜 이렇게
- 기획 수치가 **아직 확정 전**(임시값 다수) → 기획자가 코드·빌드 없이 에디터에서 바꾸고 바로 플레이 확인.
- 같은 수치를 여러 클래스가 쓰므로 한 곳에 모아 불일치 방지. 서버와 맞출 값(예: 반납 시간, 금고 시간)의 목록 역할도 한다.

### ⑤ 비교
- 코드 상수: 빠르지만 바꿀 때마다 빌드. / 데이터 테이블(CSV): 행 단위 데이터(보물 표)에 좋음 — 보물 표는 지금 배열 속성이라 나중에 데이터 테이블로 옮길 수 있음. / Config ini: 텍스트로 쉬우나 에디터에서 보기 불편.

### ⑥ 한계
- 데이터 에셋은 **서버와 자동 동기화되지 않는다** → 서버 팀원과 값 목록을 맞춰야 함.
