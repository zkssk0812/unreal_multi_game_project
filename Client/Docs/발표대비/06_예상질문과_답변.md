## C. 네트워크 (깊음)

### Q12. 패킷 구조를 설명해 보세요.
**답변**: `[size:uint16][type:uint16][body]`이고 size는 헤더 4바이트를 포함한 전체 길이입니다. 리틀 엔디언이고, 서버와 공유하는 `protocol.h`의 `#pragma pack(1)` 구조체를 그대로 `memcpy`합니다. 그래서 `VHPacket::Make<T>`가 `static_assert(std::is_trivially_copyable_v<T>)`로 memcpy 가능한 구조체인지 컴파일 때 검사합니다(`Source/MCPTest/Network/VHPacket.h`). 최대 크기는 `MAX_PACKET_SIZE = 8192`.
- 꼬리: "엔디언 변환은 안 하나요?" → 클라이언트·서버 모두 x86/x64 리틀 엔디언이라 변환 없이 복사합니다(파일 주석에 적어 둠). 다른 엔디언 기기를 지원하려면 필드별 직렬화가 필요 — 한계.
- 꼬리: "protocol.h를 왜 namespace로 감쌌나요?" → 언리얼 타입과 이름이 겹칠 수 있어서 `VHProtocol.h`에서 `<cstdint>` 등을 먼저 include한 뒤 `namespace RobProto { #include "Protocol/protocol.h" }`로 감쌌습니다. 서버와 같은 파일을 **수정하지 않고** 쓰기 위해서입니다.

### Q13. TCP에서 패킷이 잘려 오거나 여러 개가 붙어 오면 어떻게 처리하나요?
**답변**: TCP는 "바이트의 흐름"이라 보낸 단위대로 오지 않습니다. 받은 바이트를 `FVHPacketAssembler::Append`로 버퍼에 쌓고, `FVHPacketAssembler::Pop`이 앞 2바이트로 size를 읽어
- 버퍼가 4바이트(헤더)보다 적거나 size보다 적으면 `NeedMore` → 다음 수신을 기다림(잘려 온 경우),
- size만큼 있으면 패킷 하나를 꺼내 `Packet`을 돌려줌,
- size가 4 미만이거나 8192 초과면 `Error` → 연결을 끊음.
`UVHNetSubsystem::OnBytes`가 `for (;;)` 반복문으로 `Pop`을 계속 불러서 **붙어 온 여러 패킷을 한 번에** 다 처리합니다. 다 읽은 버퍼 앞부분은 비우거나 16KB가 넘으면 정리해 버퍼가 끝없이 커지지 않게 했습니다.
- 꼬리: "테스트는 했나요?" → 자동화 테스트 `VaultHeist.Net.PacketAssembler`, 그리고 `FVHMockTransport`가 서버 → 클라이언트 바이트를 **일부러 작은 조각으로 쪼개 보내는**(`bSplitPackets`) 기능이 있어 평소 실행할 때마다 재조립이 검증됩니다.
- 보여줄 파일: `Source/MCPTest/Network/VHPacket.cpp` `FVHPacketAssembler::Pop`, `VHNetSubsystem.cpp` `OnBytes`

### Q14. 받은 패킷이 이상한 크기면? 가변 길이 패킷은?
**답변**: 고정 길이 패킷은 `VHPacket::ReadFixed`가 **크기가 sizeof(T)와 정확히 같을 때만** 읽습니다. 배열이 마지막에 있는 가변 길이 패킷(방 목록 등)은 `VHPacket::ReadVariable`이 count가 최대치 이하인지, 받은 크기가 `*_Size(count)`와 정확히 같은지 검사합니다. 실패하면 `UVHNetSubsystem::HandlePacket` 안의 `Bad()`로 처리합니다.

### Q15. "단계별 패킷 제한"이 뭔가요? 왜 클라이언트도 막나요?
**답변**: 서버 명세상 연결 단계(Anonymous → Lobby → Room → Game)마다 보낼 수 있는 패킷이 정해져 있고, 허용되지 않은 패킷을 보내면 서버가 **연결을 끊습니다**. 클라이언트도 `EVHNetPhase`로 지금 단계를 추적하고, `UVHNetSubsystem::CanSend`의 표(예: Anonymous는 `CS_LOGIN`만, Lobby는 방 목록·생성·입장 등)로 보내기 전에 막습니다. 막히면 경고 로그를 남깁니다(버그 신호). 이건 일종의 **상태 머신**입니다 — 단계는 `SetPhase`로만 바뀌고 `OnPhaseChanged` 델리게이트로 UI에 알립니다.
- 꼬리: "연타는?" → 로비·방 요청은 서버가 초당 10회 제한이라 클라이언트는 `PassRateLimit`에서 초당 8회로 조금 낮게 막습니다.
- 보여줄 파일: `VHNetSubsystem.cpp` `CanSend`, `PassRateLimit`, `SendBytes`

### Q16. 하트비트는 어떻게 동작하나요?
**답변**: 모든 단계에서 2초(`PING_INTERVAL_MS = 2000`)마다 `CS_PING`을 보냅니다(`UVHNetSubsystem::Tick` → `SendPing`). 서버는 10초(`HEARTBEAT_TIMEOUT_MS`) 동안 아무것도 못 받으면 끊습니다. 클라이언트는 `SC_PONG`(`HandlePong`)으로 왕복 시간(RTT)을 재고, 15초(`ReceiveTimeoutSeconds`) 동안 아무것도 못 받으면 연결이 끊긴 것으로 처리합니다. 접속 직후 바로 한 번 보냅니다(`NextPingTime = Now`).

### Q17. 소켓 수신은 별도 스레드인가요?
**답변**: 아니요. `FVHTcpTransport`는 **논블로킹 FSocket을 게임 스레드 Tick에서 폴링**합니다(별도 수신 스레드 없음, `VHTcpTransport.h` 주석). 보낼 때 한 번에 다 못 보내면 남은 바이트를 보관했다가 다음 Tick에 이어서 보냅니다.
- 이유: 스레드를 쓰면 받은 데이터를 게임 스레드로 넘기는 큐와 동기화(락)가 필요한데, 패킷량이 적은 메뉴·로비 단계에서는 폴링이 단순하고 안전합니다. UI·게임 객체는 게임 스레드에서만 만져야 하므로 처리도 자연스럽습니다.
- 단점: 최대 한 프레임 지연, 프레임이 멈추면(로딩) 수신도 멈춤. 인게임 20Hz 이동 패킷이 본격화되면 수신 스레드 + 스레드 안전 큐(생산자-소비자)로 바꾸는 것을 고려(운영체제 수업의 생산자-소비자 문제).
- 보여줄 파일: `Source/MCPTest/Network/VHTcpTransport.cpp` `Tick`

### Q18. 가짜 서버(Mock)는 왜 만들었고, 실제 서버와 어떻게 바꾸나요?
**답변**: 서버 팀원이 처음엔 PING/PONG만 구현한 상태여서, 서버를 기다리면 클라이언트 화면을 하나도 시험할 수 없었습니다. 그래서 **같은 바이트 패킷**을 받아 프로토콜대로 응답 바이트를 돌려주는 인프로세스 가짜 서버 `FVHMockServer`를 만들었습니다. 전송 계층을 인터페이스 `IVHTransport`(Connect/Send/Tick/Disconnect)로 추상화하고 구현을 2개 — `FVHTcpTransport`(진짜 소켓)와 `FVHMockTransport`(가짜 서버) — 만들었고, `UVHNetSubsystem::ConnectAndLogin`이 `UVHSettings::bUseMockServer`를 보고 둘 중 하나를 고릅니다. **위쪽 코드(패킷 처리·UI)는 어느 쪽인지 모릅니다** → 실서버가 준비되면 설정만 바꾸면 됩니다.
- 꼬리: "Mock이 진짜 서버와 다르게 동작하면?" → 그게 가장 큰 위험입니다. Mock은 명세를 보고 만든 것이라 서버 구현과 다를 수 있어, 서버 기능이 나올 때마다 실서버로 다시 확인해야 합니다. 서버가 프로토콜 v2로 바뀐 것도 그런 예입니다(04 문서).
- 보여줄 파일: `Source/MCPTest/Network/VHTransport.h`, `VHMockTransport.h`, `VHSettings.h`

### Q19. 서버 프로토콜이 v2로 바뀌었다는데 클라이언트는 어떻게 되나요?
**답변**: 클라이언트 사본(`Source/MCPTest/Network/Protocol/protocol.h`)은 아직 v1.0이고, 접속 때 `CS_LOGIN`에 버전을 넣어서 다르면 서버가 `VersionMismatch`로 거절합니다. v2로 옮기려면 protocol.h를 서버 것으로 교체하고, 바뀐 패킷에 맞게 `UVHNetSubsystem`의 처리 함수와 `FVHMockServer`를 고쳐야 합니다. 자세한 차이는 `Docs/발표대비/04_서버연동과_역할분담.md`에 정리했습니다(이 부분은 04 문서를 먼저 공부할 것).

### Q20. 탑뷰 카메라는 어떻게 만들었나요? 벽에 캐릭터가 가려지는 문제는?
**답변**: 캐릭터의 스프링암을 월드 기준 고정 각도(피치 -65°, 거리 15m)로 바꿨습니다(`UVHAimComponent::ApplyTopDownCamera`: `SetUsingAbsoluteRotation(true)`, `bDoCollisionTest = false`). 비스듬히 내려다보니 3m 벽 뒤 약 1.4m가 가려져 캐릭터가 사라지는 문제가 있었는데, **카메라에서 내 캐릭터까지 선을 긋고 그 선 1.5m 안의 벽 픽셀만 지우는 벽 재질** `M_VHWallFade`를 만들었습니다. 캐릭터 위치는 매 프레임 `UVHAimComponent::UpdateOcclusion`이 재질 파라미터 모음 `MPC_VHOcclusion`(PlayerPos·Radius·Enabled)에 넘깁니다. 충돌·손전등 빛은 그대로이고 **보이는 것만** 바뀝니다.
- 꼬리: "재질 안의 계산은?" → Custom HLSL 노드: 카메라→캐릭터 방향 n에 픽셀 위치를 투영(t = dot)하고, 선까지 거리 r이 반경보다 작고 캐릭터보다 카메라 쪽(t < L-40)이면 OpacityMask 0. 경계 40cm는 체크무늬로 반쯤 지움.
- 보여줄 파일: `Source/MCPTest/Gameplay/VHAimComponent.cpp`, 에셋 `Content/VaultHeist/Materials/M_VHWallFade`

### Q21. 커서 기준 이동은 어떻게 계산하나요?

- 꼬리: "어떻게 검증했나요?" → 자동화 테스트 `VaultHeist.Interaction.AimMove`(커서 위·아래·좌·우·대각선 × WASD)와, PIE에서 실제 키·마우스로 84가지 경우를 로그 위치 변화로 측정.
- 보여줄 파일: `Source/MCPTest/Gameplay/VHInteractionRules.cpp` `AimRelativeMove`, `Tests/VHInteractionTests.cpp` `FVHAimMoveTest`

### Q22. 스테미나·탈진은 어떻게 동작하나요?
**답변**: `UVHActionComponent`가 관리합니다. 최대 100, 초당 10 회복, 달리기 초당 10, 구르기 20, 공격 30(`FVHCharacterStats`, `DA_VHGameplayConfig`의 Thief Stats). 0이 되면 `SetExhausted(true)` → 회복이 절반(`ExhaustedRegenMultiplier` 0.5)이고 달리기·구르기·공격 불가, **100까지 다 차면** 풀립니다(기획 PDF 10장). 무게가 무거우면 소모량이 비례해서 1배→2배(`VHRules::StaminaCostMultiplier`).

### Q23. 상호작용 대상은 어떻게 고르나요?
**답변**: `UVHInteractionComponent::TickComponent`가 매 프레임 ① 손전등 빛 안에 있거나 항상 보이는(반납지점) 오브젝트 집합을 만들고(`UVHFlashlightComponent::IsBoxLit`: 원뿔 각도·거리 + 벽에 가렸는지 라인 트레이스), ② `UpdateFocus`가 그중 **반경 1.5m 안 + 시선 좌우 75° 안**에서 거리와 각도를 합친 점수(`VHRules::TargetScore`)가 가장 좋은 것 하나를 고릅니다. ③ `UpdateOutlines`가 빛 안 오브젝트에 테두리(커스텀 스텐실)를 켭니다.
- 보여줄 파일: `Source/MCPTest/Gameplay/VHInteractionComponent.cpp`

### Q24. 우클릭(G)을 누르면 어떤 순서로 함수가 호출되나요? (중단점 질문)
**답변**:
1. Enhanced Input이 `IA_VHInteract` Started → `AVHGamePlayerController::OnInteractStarted`
2. → `UVHInteractionComponent::InteractPressed`(구르기·공격 중이면 무시, 대상이 없거나 불가면 회색 문구 다시 표시)
3. → `UVHInteractionSubsystem::GetAuthority()->RequestBegin(this, Target)` — 판정 담당(지금은 `UVHLocalInteractionAuthority`)이 `BuildOffer`로 할 수 있는지·몇 초짜리인지 결정
4. → 시작되면 `UVHInteractionSubsystem::ApplyInteract`(Begin) → 컴포넌트 `HandleInteractState`가 진행 바·이동 잠금
5. → 시간이 다 되면 판정 담당 `Tick`에서 `ResolveComplete` → 결과에 따라 `ApplySafeOpened`, `ApplySafeTreasureTaken`, `ApplyTreasureReturned` 같은 **Apply\*** 함수가 화면과 상태를 바꿈.
떼면 `InteractReleased` → `RequestCancel`(길게 누르기만), 이동 키는 `OnMoveTriggered` → `NotifyMoveInput` → `RequestCancel`.
- 보여줄 파일: `Source/MCPTest/Gameplay/VHInteractionComponent.cpp` `InteractPressed`, `VHInteractionAuthority.h`

### Q25. "판정"과 "반영"을 나눴다는 게 무슨 뜻인가요? 왜요?
**답변**: "할 수 있나, 끝나면 무엇이 되나"는 **판정 담당** `UVHInteractionAuthority` 한 곳만 정하고, 화면·상태 변경은 `UVHInteractionSubsystem::Apply*` **한 입구**로만 합니다. 지금은 클라이언트가 판정하는 `UVHLocalInteractionAuthority`이지만, 진짜 게임은 서버가 판정해야 하므로(치트 방지, 3명 동기화) 나중에 `UVHInteractionAuthority`를 상속한 "서버 판정 클래스"가 요청을 패킷으로 보내고, 받은 결과 패킷으로 **같은 Apply\***를 부르면 됩니다. 오브젝트·컴포넌트·HUD는 고칠 필요가 없습니다.
- 꼬리: "지금 바로 바꿀 수 있나요?" → 구조는 준비됐지만 서버 판정 클래스는 아직 없음(서버 인게임 구현 + v2 연동 필요). 한계로 솔직히 말할 것.

### Q26. 금고 진행도는 어떻게 유지되나요? 30초를 40초로 바꾸면?
**답변**: 진행도를 "몇 초"가 아니라 **비율(0~1)**로 저장합니다(`FVHHoldProgress`, `VHInteractionRules.h`). 떼면 `Cancel`에서 지금까지의 비율을 보관(금고는 `bSafeKeepProgress` 켬)하고, 다시 시작하면 남은 비율만큼만 진행합니다. 그래서 기획이 시간을 바꿔도 "1/3 열림"은 그대로 자연스럽고, 서버가 "시작 시각 + 남은 시간"을 줘도 같은 식으로 계산됩니다(`BeginWithRemaining`). 창고 문(구출)은 떼면 0으로 초기화(`bRescueKeepProgress` 끔).

### Q27. 동시에 1명만 쓰게 하는 건 어디서 하나요?
**답변**: 판정 담당이 진행 중인 세션 목록을 보고, 다른 의적이 그 대상을 쓰고 있으면 거절 사유 Busy(`"다른 의적이 사용 중입니다"`)를 돌려줍니다(`Source/MCPTest/Gameplay/VHInteractionAuthority.cpp`). 개발용 `VHDummyUse Safe_1`로 더미 의적이 먼저 쓰게 해서 확인했습니다.

### Q28. 손전등 빛 안에서만 테두리가 생기는 원리는?
**답변**: 오브젝트 메시에 **커스텀 뎁스 스텐실 번호**를 찍습니다(`AVHInteractableBase::SetOutline`: 1 빛 안, 2 지금 대상, 3 불가). 화면 전체에 붙인 포스트 프로세스 재질 `M_VHOutline`이 스텐실 값이 바뀌는 **경계 픽셀에만** 색을 칠합니다(`AVHGamePlayerController::ApplyOutlinePostProcess`가 카메라에 붙임, 프로젝트 설정 `r.CustomDepth=3`). 반납지점은 항상 보이게(`IsAlwaysVisible`).
- 꼬리: "예전 방식은?" → 처음엔 메시에 반투명 재질을 덧씌웠는데 평평한 도형이면 면 전체가 칠해져서 포스트 프로세스 방식으로 바꿨습니다.

### Q29. 반납지점 규칙(방마다 최대 1개, 항상 5곳)은 어떻게 구현했나요?
**답변**: `UVHMatchSubsystem`이 레벨의 방 지역(`AVHRoomVolume`) 중 반납지점이 허용되고 아직 없는 방을 골라 `SpawnReturnPoint`로 만들고, 방 안의 빈 바닥은 `AVHRoomVolume::FindRandomFloorPoint`(아래로 라인 트레이스 + 그 자리에 막는 게 없는지 겹침 검사)로 찾습니다. 50초에 빨강, 60초에 사라지거나 반납되면 **방금 사라진 방을 제외한** 다른 방에 새로 만들어 항상 5곳을 유지합니다(기획 PDF 2장).
- 보여줄 파일: `Source/MCPTest/Gameplay/VHMatchSubsystem.cpp`, `VHRoomVolume.cpp`

### Q30. 탈출부터 결과창까지의 흐름은?
**답변**: 반납 가치가 10,000$가 되면 `UVHMatchSubsystem::UnlockExit`가 배너를 띄우고 탈출구를 엽니다. 열린 `AVHExitGate`의 트리거(`EscapeTrigger`)에 들어가면 `UVHMatchSubsystem::HandleEscapeZone` → `EndMatch` → 3초 뒤 `UVHNetSubsystem::ReportLocalMatchEnd`로 결과를 보고 → Mock은 `FVHMockServer::ClientReportsMatchEnd`로 `SC_GAME_END`를 만들어 보냄 → `UVHNetSubsystem::HandleGameEnd`가 메뉴 레벨을 열고 결과창을 띄웁니다. 시간 초과도 `UVHMatchSubsystem::Tick`에서 `EndMatch`로 같은 길을 탑니다.
- 꼬리: "실서버에서도 클라이언트가 결과를 보고하나요?" → 아니요. 진짜로는 **서버가 판정하고** `SC_GAME_END`를 보내야 합니다. 클라이언트 보고는 Mock 전용 통로(프로토콜 밖)입니다 — 한계.

### Q31. 공격과 경직은?
**답변**: 좌클릭 → `UVHActionComponent::RequestAttack`(탈진이면 거절, 스테미나 30) → 1초 중 앞 20%(0.2초)는 준비, 다음 50%(0.5초) 동안 `SweepAttack`이 시선 방향 120°·1.5m 부채꼴(`VHRules::IsInAttackFan`) 안의 대상을 찾아 판정 담당 `ResolveAttackHit`에 넘깁니다. 경비원이면 `UVHInteractionSubsystem::ApplyStun` → 3초 경직(들고 있던 보물 전부 바닥에 떨어뜨림), 이후 10초 면역. 맞음/빗나감에 따라 소리 20m/5m.
- 꼬리: "공격 범위 1.5m는 어디서?" → 기획은 "캐릭터 신체에 비례"라 임시값 1.5m(`AttackRadius`, 확인 필요). PIE에서 2m 떨어진 경비원이 안 맞아서 범위가 실제로 1.5m+캡슐 반경임을 확인했습니다.

### Q32. 소리 시스템은? 경비원이 실제로 듣나요?
**답변**: `UVHMovementNoiseComponent`가 동작별 간격(걷기 0.5초, 달리기 0.2초, 구르기 매 프레임)으로 소리 신호(`FVHNoiseEvent`)를 `UVHInteractionSubsystem::ReportNoise`에 보냅니다. 반경은 기획 PDF 8장 표대로(걷기 0m, 달리기 12m, 구르기 15m) + 보물 개당 2m, 최종 ×1.1(`VHRules::NoiseRadius`). **하지만 소리를 듣고 움직이는 경비원 AI는 아직 없습니다.** 지금은 바닥 원(디버그 표시)과 HUD 신호 수로만 확인합니다 — 다음 단계.

### Q33. 맵은 어떻게 가져왔나요? 충돌은?
**답변**: 모델러의 FBX를 `SM_Mansion_1F`로 가져왔습니다. 충돌 박스 98개의 이름이 언리얼 규칙(`UCX_`)이 아니었지만 메시 안의 보이지 않는 충돌 요소로 들어왔고, 선택지 중 (가) "벽 메시 자체를 충돌로"(Use Complex Collision As Simple)를 골랐습니다 — 보이는 벽과 충돌이 항상 같고, 리임포트해도 설정이 유지되는 것을 실제로 확인했습니다. 레벨에서 -90° 돌려 평면도 위쪽이 화면 위쪽이 되게 했고(언리얼 X = 평면도 Y×100, Y = 평면도 X×100), 방 33곳을 벽 좌표로 나눠 `AVHRoomVolume`을 놓았습니다(문 없는 방 3곳은 반납지점 제외).
- 보여줄 파일: `Docs/맵_교체_가이드.md`, `Docs/Mansion_1F_지역.png`

### Q34. 금고 10곳 중 5곳만 나오게 한 건 어디서? 목표를 못 채우면?
**답변**: `UVHInteractionSubsystem::AssignSafeTreasures`가 게임 시작 직후 금고 후보를 섞어 `ActiveSafeCount`(5)개만 남기고 나머지는 숨기고 충돌을 끄고 상호작용 대상에서 뺍니다. 보물 10종은 **가장 싼 5개 합이 11,000$**가 되게 짜서 어느 5개가 나와도 목표 10,000$를 채울 수 있습니다.
- 꼬리: "서버와 같은 금고가 나와야 하지 않나요?" → 맞습니다. 지금은 클라이언트가 무작위로 고르는데, 실서버에서는 서버가 정해서 알려줘야 합니다(서버 요청 목록에 있음).

## E. 검증·AI 활용·태도 (깊음)

### Q35. AI가 짠 코드를 어떻게 검증했나요?
**답변**: 세 단계로 했습니다.
1. **자동화 테스트** 6개(`VaultHeist.*`): 패킷 재조립, Mock 서버 흐름, 소지 규칙·무게, 진행도, 판정 흐름(경직·탈출 등), 커서 기준 이동. 에디터 "창 → 테스트 자동화"에서 실행.
2. **PIE 실행 확인**: 기능마다 실제로 플레이하고 출력 로그(`[Interact]`, `[Match]`, `[Attack]`, `[Move]`)와 화면 캡처로 확인. 키를 누르고 있는 동작은 OS 입력으로 실제 키를 눌러 확인했습니다.
3. **단계마다 커밋**: 기능 하나가 확인되면 커밋해서, 문제가 생기면 어느 단계에서 생겼는지 되돌아볼 수 있게 했습니다.
그리고 AI가 처음에 틀린 것들(예: Shift 달리기 미인식, 배치안 그림의 방 번호 오류, 테스트 컴파일 오류)을 이 확인 과정에서 잡았습니다 → `03_문제해결_사례.md`.

### Q36. 본인이 직접 결정한 것은 무엇인가요?
**답변**: 기획 해석과 설계 선택은 제가 했습니다. 예: 상호작용 키 우클릭+G, 무게는 비례 감속(0kg 0% → 20kg 50%), 빛 안에서만 상호작용하되 반납지점·숨은 상태 나오기·이미 시작한 길게 누르기는 예외, 공격 중 이동 가능, 맵 충돌은 벽 메시 자체로, 맵 방향은 평면도와 같게, 캐릭터 앞 벽은 투명하게, 탈출구는 서쪽 옆문, 정문은 투명 벽, 커서 기준 이동(팀 결정)과 그 세부 가정. 각 결정의 이유는 `05_AI활용_방식.md`와 작업보고의 "사용자 결정" 표에 있습니다.

### Q37. 이 프로젝트의 가장 큰 한계는?
**답변**: ① 경비원 AI가 없어 핵심 긴장감(들키기·잡히기)이 아직 없음, ② 게임 판정을 클라이언트가 하고 있고, **실서버에는 아직 한 번도 접속해 보지 않았음**(TCP 전송 코드는 있지만 PING/PONG도 미확인 — 10-16 보고서 "확인하지 못한 것"), 모든 흐름은 Mock으로만 확인, ③ 클라이언트 프로토콜이 v1이라 v2로 옮겨야 하고, 서버 v2의 게임 규칙(반납 보물 3개면 탈출, 1인 3개, 정문 탈출)·맵 좌표(회전 없음)가 우리 클라이언트(10,000$, 20kg·10개, 서쪽 옆문, -90° 회전)와 다름 → 팀이 어느 기준을 따를지 정해야 함(04 문서), ④ 캐릭터·애니메이션·UI 디자인이 임시(마네킹, 머리 위 화살표), ⑤ 맵 초안의 문 없는 방 3곳. 각각 다음 단계가 작업보고 "다음 단계"에 있습니다.

### Q38. 다시 만든다면 무엇을 다르게 하겠나요?
**답변(예시)**: 서버 팀원과 인게임 패킷(판정 결과·반납지점·스테미나 상태)을 더 일찍 합의했다면 클라이언트 판정을 서버 판정으로 옮기기가 쉬웠을 것입니다. 또 수신을 처음부터 스레드+큐 구조로 설계하거나, 입력 키 이름을 화면 문구에 매핑에서 읽어 오게 했으면 좋았을 것입니다.
