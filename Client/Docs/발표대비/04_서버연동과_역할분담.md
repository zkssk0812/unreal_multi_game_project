## 1. 클라이언트와 서버는 무엇을 나눠 맡나

이 게임은 **권위 서버(authoritative server)** 구조를 목표로 한다. "누가 진짜 결과를 정하나"가 핵심이다.

| 일 | 서버(팀원, C++ IOCP) | 클라이언트(나, 언리얼) |
|---|---|---|
| 접속·로그인·방 | 이름 중복 검사, 방 목록·생성·입장, 캐릭터 중복 검사, 전원 준비 시 시작 | 화면(메인·로그인·로비·대기실), 입력 검사(영문 2~12자 등), 요청 보내기, 받은 상태 그리기 |
| 게임 규칙 결과 | 금고가 열렸나, 보물이 누구 것인가, 잡혔나, 탈출했나, 이겼나 (**서버만 정함**, `docs/DESIGN.md` 1장 "서버 권위 원칙") | 요청만 보냄(`CS_ACTION`). 결과 패킷을 받아 연출 |
| 이동 | 클라가 보낸 위치를 **그대로 받아** 남에게 전달 (검증·보정 없음, `DESIGN.md` 1장·6.2) | 입력 → 캐릭터 이동(언리얼 CharacterMovement), 위치를 `CS_MOVE`로 보냄 |
| 경비원(NPC) | 서버에서만 생각하고 움직임(상태 머신, A*, 시야, 소리) | 받은 위치를 그림 |
| 화면 연출 | 없음 | 카메라, 손전등 빛, 테두리, 진행 바, HUD, 결과창 |

- 서버 문서의 한 줄 요약: "게임 규칙의 결과는 **서버만** 정합니다. 클라는 요청만 보냅니다." (`DESIGN.md` 1장)
- 단, 이동은 3인 PvE 졸업작품이라 부정행위 방지를 다루지 않기로 해서 **클라가 정한 위치를 서버가 그대로 쓴다** (v2 `CS_Move.pos` 주석: "클라가 정한 위치를 서버가 그대로 쓴다").

### 지금(2026-10-26) 실제 상태
- 서버 팀원의 서버는 v2로 로비·방·게임 규칙·경비원 AI까지 구현 완료(ROADMAP P0~P5 완료, P6 진행 중 — 3장 참고).
- **내 클라이언트는 아직 v1.0 프로토콜**이고, 게임 규칙 판정은 **클라이언트가 직접** 한다(`UVHLocalInteractionAuthority`, `UVHMatchSubsystem`). 서버에 붙는 부분은 메뉴~대기실~결과창 흐름과 PING/PONG까지.
- 그래서 지금은 **실서버로 한 판을 끝까지 할 수 없다.** 이것을 숨기지 말고 "서버 판정으로 갈아끼울 수 있게 구조를 나눠 두었고, v2로 옮기는 작업이 남았다"고 설명한다.

## 2. 왜 판정은 서버가 해야 하나

### 2-1. 이유 세 가지
1. **치트 방지**: 판정을 클라가 하면, 클라 메모리를 고쳐 "금고 열림", "보물 100개"를 만들 수 있다. 서버가 정하면 클라를 고쳐도 결과는 안 바뀐다.
2. **동기화(모두가 같은 결과를 봄)**: 3명이 같은 금고를 동시에 열면 누가 먼저인가? 각자 판정하면 화면마다 결과가 다르다. 한 곳(서버)이 정하고 모두에게 알리면 하나로 맞는다. 예: "금고는 한 번에 한 명"(v2 `RejectReason::TargetBusy`).
3. **NPC는 한 곳에서만 움직여야 함**: 경비원이 클라마다 따로 움직이면 사람마다 경비원 위치가 다르다. 그래서 경비원 AI는 서버에만 있다.

> 용어: **권위 서버** = 진짜 상태를 가진 쪽이 서버. 클라는 "보이는 것"을 담당.
> **클라이언트 예측** = 응답을 기다리면 느리니까 클라가 먼저 연출하고, 서버가 거절하면 되돌림. v2에도 이 개념이 있다: `SC_ActionReject` 주석 "클라가 미리 재생한 연출을 되돌린다".

### 2-2. 우리 코드는 "판정 계층"을 갈아끼울 수 있게 나눠 두었다
핵심 파일: `Source/MCPTest/Gameplay/VHInteractionAuthority.h`

```
키 입력 → 컴포넌트(UVHInteractionComponent 등)
            │ 요청: RequestBegin / RequestCancel / RequestFlashlight   (= CS_ACTION)
            ▼
   UVHInteractionAuthority  (UCLASS(Abstract), 판정만 담당)
      └ 지금: UVHLocalInteractionAuthority  (클라가 직접 판정)
      └ 나중: 서버용 판정 클래스(아직 없음)  → 요청을 CS_ACTION 패킷으로 보냄
            │ 결과
            ▼
   UVHInteractionSubsystem::Apply*   (화면·상태 반영의 유일한 입구)
            ▼
   오브젝트 액터(연출) / 컴포넌트(상태) / HUD
```

- 헤더 주석 그대로: "서버가 판정하게 되면 이 클래스를 상속한 서버용 판정 클래스를 만들어 RequestBegin/Cancel → C_ACTION 패킷 전송, 받은 SC_ 패킷 → Subsystem의 Apply* 호출로 바꾸면 된다. Evaluate(안내 문구용 예측)는 로컬 규칙을 그대로 써도 된다."
- 어디서 고르나: `UVHInteractionSubsystem::Initialize`(`VHInteractionSubsystem.cpp` 42행) — `Authority = NewObject<UVHLocalInteractionAuthority>(this);`. 서버 판정으로 바꿀 때는 **이 한 줄과 새 클래스**가 바뀌고, 오브젝트·컴포넌트·HUD는 그대로 둔다.
- 가상 함수 목록(`UVHInteractionAuthority`): `Evaluate`, `RequestBegin`, `RequestCancel`, `RequestFlashlight`, `Tick`, `NotifyThiefStatusChanged`, `NotifyTargetRemoved`, `NotifyActorStunned`, `ResolveAttackHit`.
- 비유: 판정 담당을 "심판"으로 생각하면 된다. 지금은 내 컴퓨터 안의 심판(Local), 나중에는 서버 심판에게 전화(패킷)해서 결과를 듣는다. 선수(컴포넌트)와 전광판(HUD)은 심판이 바뀌어도 그대로다.

### 2-3. 아직 클라이언트가 직접 하고 있는 판정 (서버로 옮겨야 할 것)
| 지금 클라에서 하는 일 | 파일·함수 | v2에서 대신 받을 패킷 |
|---|---|---|
| 상호작용 가능 여부·완료 | `UVHLocalInteractionAuthority::Evaluate / RequestBegin / Tick` | `SC_INTERACT`(Begin/Cancel/Complete), `SC_ACTION_REJECT` |
| 금고 열림·보물 줍기 | `UVHInteractionSubsystem::ApplySafeTreasureTaken` 등 | `SC_SAFE_OPENED`, `SC_TREASURE` |
| 공격 명중·경직 | `UVHLocalInteractionAuthority::ResolveAttackHit`, `UVHInteractionSubsystem::ApplyStun` | `SC_ATTACK`, `SC_HIT`(`HitOutcome::Captured/Stunned`) |
| 반납·탈출구 열림·탈출 | `UVHMatchSubsystem`(반납 가치 합계, `CheckExitUnlock`, `HandleEscapeZone`) | `SC_TREASURE.delivered_total / can_escape`, `SC_ESCAPED` |
| 금고 10곳 중 5곳 고르기 | `UVHInteractionSubsystem::AssignSafeTreasures`(무작위) | `SC_GameLoad.safe_slots[SAFE_COUNT]` |
| 게임 끝·결과 | `UVHMatchSubsystem::EndMatch` → `UVHNetSubsystem::ReportLocalMatchEnd` → (Mock만) `FVHMockServer::ClientReportsMatchEnd` | `SC_GAME_END` |

`UVHNetSubsystem::ReportLocalMatchEnd`(`VHNetSubsystem.cpp` 1005행~)의 주석: "실제 서버: 서버가 스스로 판정해 SC_GAME_END 를 보낸다(지금은 게임 판정 패킷이 없어 오지 않음 → 서버 요청 목록)". 즉 **"클라가 결과를 보고"하는 건 Mock 전용 임시 방식**이다.

## 3. 가짜 서버(Mock)로 개발한 이유와 구조

### 3-1. 왜 Mock인가
- 시작할 때(2026-10-16) 서버는 `CS_PING`/`SC_PONG`만 처리했고, 모르는 패킷을 받으면 연결을 끊었다(CLAUDE.md "현재 서버 구현 상태").
- 서버를 기다리면 클라이언트 화면(로그인·로비·대기실·결과창)을 만들 수 없다. 그래서 **같은 바이트 패킷을 받아 프로토콜대로 응답하는 가짜 서버를 클라 안에** 만들었다.
- 핵심은 "가짜 서버도 **진짜 바이트**를 주고받는다"는 것. 패킷 조립·분해·단계 검사 코드는 실서버와 똑같이 거친다. 그래서 실서버로 바꿀 때 **설정 하나**(`bUseMockServer`)만 바꾸면 된다.
- 개발 중 테스트가 쉽다: 가짜 플레이어 2명이 몇 초 뒤 들어와 준비하는 연출(`FVHMockConfig::FakePlayersInNewRoom`, `UVHSettings::MockFakePlayers`)로 혼자서도 "전원 준비 → 게임 로드"를 확인했다.

### 3-2. 구조 (전송 계층 교체)
```
UI 위젯들 ─┐
          ▼
UVHNetSubsystem  (UGameInstanceSubsystem: 레벨이 바뀌어도 살아 있음)
  - 단계(Phase) 추적, 허용 패킷 검사(CanSend), 연타 방지(PassRateLimit)
  - 2초마다 CS_PING, 15초 무응답이면 끊김 처리
  - 받은 바이트 → FVHPacketAssembler(재조립) → HandlePacket(디스패처) → 델리게이트로 UI에 알림
          │ IVHTransport 인터페이스만 앎 (Connect / Send / Tick / OnBytesReceived ...)
          ▼
 ┌──────────────────────┬──────────────────────────────┐
 │ FVHTcpTransport      │ FVHMockTransport             │
 │ 진짜 서버 (FSocket)   │   └ FVHMockServer (가짜 서버) │
 └──────────────────────┴──────────────────────────────┘
        bUseMockServer = false            bUseMockServer = true(기본)
```

| 클래스·파일 | 역할 (실제 코드 기준) |
|---|---|
| `IVHTransport` (`Network/VHTransport.h`) | 전송 계층 인터페이스. "바이트 흐름"만 주고받는다. 주석: "패킷 재조립과 해석은 서브시스템이 공통으로 한다. 모든 콜백은 Tick() 안에서, 즉 게임 스레드에서 호출된다." |
| `FVHTcpTransport` (`Network/VHTcpTransport.h/.cpp`) | 주석: "논블로킹 FSocket을 게임 스레드 Tick에서 폴링한다(별도 수신 스레드 없음)", "한 번에 다 못 보내면 남은 바이트를 보관했다가 다음 Tick에 이어서 보낸다"(`FlushSend`) |
| `FVHMockTransport` (`Network/VHMockTransport.h/.cpp`) | 가짜 서버를 품은 전송. `bSplitPackets`가 켜지면 서버 응답을 **1~97바이트씩 무작위로 잘라** 넘긴다(`VHMockTransport.cpp` 90행). TCP처럼 패킷이 잘려 와도 재조립이 되는지 매번 시험하는 장치 |
| `FVHMockServer` (`Network/VHMockServer.h/.cpp`) | 서버 흉내: 로그인, 방 목록(가짜 방), 생성·입장·퇴장, 캐릭터·퍽·준비, 전원 준비 시 `SC_GAME_LOAD`, 결과 `SC_GAME_END`. `IsAllowed`로 **단계별 허용 패킷을 서버와 똑같이 검사**하고 위반 시 `Kick`. `Epoch`로 예약된 가짜 행동을 무효화. `CS_MOVE`/`CS_ACTION`은 "게임 플레이는 아직 없으므로 무시" |
| `FVHPacketAssembler` (`Network/VHPacket.h/.cpp`) | TCP 스트림 재조립. `Pop`이 `NeedMore`(아직 덜 옴) / `Packet`(하나 완성) / `Error`(size < 4 또는 > 8192) 중 하나를 돌려준다 |
| `VHProtocol.h` | 서버의 protocol.h를 **고치지 않고** `namespace RobProto { #include "Protocol/protocol.h" }`로 감싸는 래퍼(언리얼 이름 충돌 방지) |
| `UVHSettings` (`Network/VHSettings.h`, `Config/DefaultGame.ini`) | `bUseMockServer = true`, `ServerHost = "127.0.0.1"`, `ServerPort = 9000`, Mock 옵션(`bMockSplitPackets`, `MockGameTimeoutSeconds = 330`, `MockResultScreenMs`, `MockFakePlayers`, `MockFakeActionDelaySeconds`) |

### 3-3. 서버 규칙을 클라이언트도 지키는 부분
- **단계별 허용 패킷**: `UVHNetSubsystem::CanSend`(`VHNetSubsystem.cpp` 337행~) 주석 "서버 명세의 '연결 단계별 허용 C_ 패킷'과 같은 표". 허용 안 된 패킷은 보내지 않고 경고 로그만 남긴다(보내면 서버가 끊으므로).
- **연타 방지**: `PassRateLimit` — 로비·방 요청을 초당 8회까지(`RequestLimitPerSecond = 8`, 주석 "서버 제한(초당 10회)보다 조금 낮게"). ※ v2 서버는 빈도 제한 자체를 없앴다(4장).
- **하트비트**: `PING_INTERVAL_MS`(2000)마다 `SendPing`. `SC_PONG`으로 RTT와 서버 시각 차이(`ServerTimeOffsetMs`)를 계산(`HandlePong`, 주석 "서버 시각 ≈ 받은 server_time + RTT/2"). 15초(`ReceiveTimeoutSeconds = 15.0`) 동안 아무것도 못 받으면 끊긴 것으로 처리. 서버 쪽은 10초(`HEARTBEAT_TIMEOUT_MS`) 무패킷이면 끊는다.

### 3-4. Mock의 한계 (숨기지 말 것)
- Mock은 **v1.0 프로토콜**을 흉내 낸다. 실제 서버는 이미 v2라서, Mock이 통과한다고 실서버와 맞는다는 보장이 없다.
- Mock은 게임 판정을 하지 않는다(이동·행동 무시). 게임 결과는 클라가 보고한 값(`ClientReportsMatchEnd`)으로 만든다. Mock 점수 공식도 임시.
- 가짜 플레이어는 항상 "탈출 못 함"으로 처리.

## 4. 프로토콜 v1 → v2: 무엇이 바뀌었나

> 비교 대상: 클라 `Source/MCPTest/Network/Protocol/protocol.h`(v1.0) ↔ 서버 `Docs/ServerRef/Project_Rob-master/Shared/Protocol/protocol.h`(v2.0).
> v2 머리말: "클라이언트–서버 프로토콜 v2 (기획서 수정안 기준, docs/DESIGN.md 4장)". 서버 쪽 파일 위치도 `Shared/protocol.h` → `Shared/Protocol/protocol.h`로 바뀌었다.
> 공통 규칙(바뀌지 않음): `[size:uint16][type:uint16][body]`, 리틀 엔디언, `#pragma pack(1)`, 최대 8192바이트, 포트 9000, `PING_INTERVAL_MS 2000`, `HEARTBEAT_TIMEOUT_MS 10000`, `PHASE_CHANGE_GRACE_MS 1000`, 이름 48바이트·방 이름 60바이트, 방 최대 3명, 퍽 최대 3개.

### 4-1. 버전·상수
| 항목 | v1.0 | v2.0 |
|---|---|---|
| `PROTOCOL_VERSION` | `(1u << 16) \| 0u` | `(2u << 16) \| 0u` → **정확히 같아야 접속**이므로 지금 클라는 실서버에 `VersionMismatch`로 거절됨 |
| 틱 | `TICK_HZ = 30`, `SNAPSHOT_HZ = 20` | `TICK_HZ = 20`("서버 틱 = 스냅샷 주기"), `SNAPSHOT_HZ` 삭제 |

### 4-6. 흐름에서 달라지는 점 (서버 `docs/DESIGN.md` 5·6장 기준)
- **결과 뒤에는 대기실이 아니라 메인(Lobby)으로** 돌아가고 방은 사라진다("기획서 흐름대로 메인 화면(Lobby 단계)으로 복귀하고 방은 사라짐"). → 지금 클라 결과창의 [대기실로] 버튼은 v2에서 쓸 수 없다.
- 방 옵션(맵·난이도) 없음, 방 목록 페이지 없음(대기 중인 방만 최대 20개), 전적·프로필 없음 → 로비의 "내 전적" 패널, 대기실의 맵·난이도 콤보, 방 만들기의 난이도 선택은 v2에서 쓸 곳이 없다.
- 이름 규칙: 서버 1~12자(UTF-8, 앞뒤 공백 제거, 영문 대소문자 무시 중복 검사). 클라는 사용자 결정으로 "영문 2~12자"만 허용 → 서버보다 좁으므로 충돌은 없다.
- 1명이어도 전원 준비면 시작(시연·시험용). 준비 중에 캐릭터·퍽을 바꾸면 준비 해제.
- 경기 중에는 매 틱(20Hz) `SC_SNAPSHOT`, 같은 틱의 이벤트(4000번대)를 먼저 보내고 스냅샷을 나중에 보낸다.

### 꼬리 질문 대비
- Q. 서버 버전이 다르면 어떻게 되나요? → `CS_Login.protocol_version`이 `PROTOCOL_VERSION`과 정확히 같아야 하고, 다르면 서버가 `SC_LOGIN(VersionMismatch)` 후 끊는다(`DESIGN.md` 4장). 클라 `HandleLogin`은 실패 코드별 한국어 안내를 띄운다.
- Q. 이동은 왜 검증 안 하나요? → 서버 팀 결정: 3인 PvE 졸작이라 부정행위 방지를 다루지 않고, 서버는 클라 위치를 그대로 쓴다(`DESIGN.md` 1장, 10장 "서버 이동 검증과 보정 패킷(SC_MOVE_CORRECTION)… 뺌"). 대신 규칙 결과(금고·포획·승패)는 서버만 정한다.
- Q. Mock을 실서버로 바꾸려면? → `Config/DefaultGame.ini`의 `[/Script/MCPTest.VHSettings]`에 `bUseMockServer=False`(+ `ServerHost`, `ServerPort`). 다만 지금은 v2 전환이 먼저 필요하다.
- Q. TCP에서 패킷이 잘려 오면? → `FVHPacketAssembler::Pop`이 헤더의 size만큼 모일 때까지 `NeedMore`를 돌려주고 기다린다. Mock은 일부러 1~97바이트로 잘라 보내 이것을 늘 시험한다.
