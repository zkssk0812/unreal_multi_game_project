# 05. AI(Claude Code) 활용 방식 — 정직하게 정리

> 근거: `CLAUDE.md`, `Docs/작업보고_2026-10-16/23/25/26.md`, `Docs/상호작용_설계_초안.md`, git 커밋 기록, 개발 대화 기록(질문·답변).
> 원칙: **내가 한 일을 부풀리지 않는다.** 코드 대부분은 AI가 썼고, 나는 방향을 정하고, 선택하고, 결과를 확인했다. 그 대신 "AI가 쓴 코드를 내가 설명할 수 있는가"를 이 학습 자료로 준비한다.

---

## 1. 한 문장 요약 (발표용)

> "Claude Code를 **개발 파트너**로 썼습니다. 저는 기획을 해석해 요구사항과 작업 순서·검증 기준을 정하고, AI가 제시한 선택지 중에서 결정했습니다. AI는 C++ 코드 작성, 에디터 조작(MCP), 빌드·테스트 실행을 했고, 저는 단계마다 PIE(에디터 플레이)·자동화 테스트·작업 보고서로 결과를 확인한 뒤 커밋하게 했습니다."

## 2. 역할 구분

| 구분 | 내가 한 것 | AI(Claude Code)가 한 것 |
|---|---|---|
| 기획 해석 | 기획서·`게임_시스템.pdf`와 팀 회의 결과를 읽고 무엇을 만들지 정함. 기획에 없는 부분의 임시 규칙(가정)을 정함 | 기획 문서를 읽고 모순·빈칸을 찾아 질문, 설계 문서(`상호작용_설계_초안.md`)를 정리 |
| 요구사항 | 단계별 작업 지시서 작성(예: "저택 맵 교체 7단계", "이동 기준 변경"), 주의사항(삭제 전 확인, push 금지 등) | 지시를 단계로 나눠 진행, 단계마다 결과 보고 |
| 설계 선택 | 선택지 중 결정(3장 목록) | 선택지와 장단점·추천을 제시 |
| 구현 | (직접 작성한 C++ 코드는 거의 없음) 에디터에서 빈 레벨 `L_MainMenu` 만들기 등 AI가 도구로 못 하는 조작 | C++ 코드 작성, MCP로 에셋·레벨·재질 생성, 빌드 |
| 검증 기준 | "단계마다 PIE로 확인하고 커밋", "실제 레벨 위치와 맞는지 이미지로 확인", "커서 여러 방향 × WASD × 손전등 켜고/끄고" 같은 확인 기준 지정 | 기준대로 PIE·자동화 테스트·로그·캡처로 확인하고 표로 보고 |
| 문제 대응 | 에디터 DLL 오류 때 증상·원인 추정·대응 순서를 직접 지시 | 로그 분석, 재빌드·재실행, 원인 기록 |
| 협업 | 서버 팀원·모델러와 소통, push 시점 결정 | 서버 팀원 질문·모델러 요청 목록 작성 |

**솔직한 한계**: 코드를 한 줄씩 내가 짠 것은 아니다. 그래서 교수님 질문에 대비해 이 폴더의 문서로 구조와 원리를 공부하고, `08_직접해보기.md`의 실습으로 직접 고쳐 보며 이해를 확인한다.

## 3. CLAUDE.md로 정한 작업 원칙

`CLAUDE.md`는 AI가 이 프로젝트에서 항상 지켜야 할 규칙 문서다(내가 요구사항으로 정리). 핵심만 인용:

1. "시작 시 프로젝트 상태, MCP 연결, 사용 가능한 도구부터 확인한다. 접근 못 하면 연결된 것처럼 말하지 않는다."
2. "작은 플레이 가능한 단위부터 만들고, 기능 하나마다 실행 결과를 확인한다."
3. "기능 하나가 끝날 때마다 커밋. `git push`, `git reset --hard`, 강제 삭제 금지."
4. "**`.uasset`, `.umap`은 절대 텍스트로 수정하지 않는다.** 에셋은 MCP 도구나 에디터 기능으로만 다룬다."
5. "**삭제, 대규모 구조 변경, 유료 서비스는 사용자 확인 후.**"
6. "핵심 로직은 **C++**, 조립·수치 조정은 C++을 상속한 **블루프린트**에서 하도록 설계한다."
7. "필요하면 사용자에게 물어보면서 진행한다 … 사소한 구현 세부사항은 합리적으로 정해 진행하고 보고서 '확인 필요'에 기록한다."
8. "항상 한국어로 답변한다." (2026-10-23 내 요청으로 추가)

그 밖에 CLAUDE.md에 정한 것: 서버 프로토콜 파일(`protocol.h`)은 **내용을 고치지 않고** 그대로 복사해 쓰기, 네트워크를 TCP/가짜 서버(Mock)로 교체 가능하게 만들기, 작업마다 `Docs/작업보고_날짜.md`에 **변경 내용 / 테스트 결과 / 남은 문제 / 확인 필요 / 서버 팀원 질문 / 다음 단계 / 발표 대비 메모** 형식으로 남기기.

**왜 이렇게 했나**: AI는 빠르지만 내가 안 보는 사이 큰 변경을 할 수 있다. 그래서 "되돌리기 어려운 일은 먼저 묻기", "에셋은 도구로만", "기능마다 확인·커밋"을 규칙으로 고정했다. 실제로 삭제가 필요할 때는 목록을 받아 확인한 뒤 진행했다(예: 2026-10-25 레벨의 바닥 보물·벽 일부 삭제).

## 5. 단계마다 검증하고 커밋한 방식

1. **작은 단계로 나누기**: 예) 2026-10-25는 12단계, 2026-10-26 저택 작업은 7단계. 단계마다 커밋(커밋 메시지에 "(N단계)" 표시, `git log`로 확인 가능).
2. **PIE(에디터 플레이)로 확인**: AI가 MCP로 PIE를 켜고, 콘솔 명령(`VHGoto`, `VHAddValue`, `VHSetTime` 등)으로 상황을 빠르게 만든 뒤
   - **로그**(`[Interact]`, `[Match]`, `[Treasure]`, `[Attack]`, `[Move]` 등)로 동작을 확인,
   - **화면 캡처**로 보이는 결과를 확인,
   - 키를 "누르고 있는" 동작은 MCP로 못 보내서 **운영체제 입력**(키보드·마우스 이벤트)으로 실제로 눌러 확인.
3. **자동화 테스트**: 순수 계산(무게·속도 배율·소리 반경·공격 부채꼴·커서 기준 이동)과 판정 흐름을 테스트 6개로 매번 검사(`Gameplay/Tests/VHInteractionTests.cpp`, `Network/Tests/VHNetTests.cpp`). 에디터 메뉴 창 → 테스트 자동화 → `VaultHeist`.
4. **보고서**: 무엇을 확인했고 **무엇을 확인하지 못했는지**를 따로 적게 했다(예: "실서버 연결은 확인 못 함", "내비 메시 길찾기는 AI가 없어 확인 못 함").
5. **커밋 → push는 별도**: 커밋은 단계마다, push는 내가 상태를 확인하고 지시할 때만. push 전후로 "원격과 같은 커밋인지, `main`·`function/camera`는 그대로인지"를 확인하게 했다.

## 6. AI에 맡긴 부분을 내가 어떻게 이해·검증했는가

| 방법 | 예 |
|---|---|
| 결과를 숫자로 확인 | 달리기 600cm/s, 구르기 0.5초에 453cm, 이동 방향 84가지 오차 0~3° 같은 측정값으로 "된다/안 된다"를 판단 |
| 기획과 대조 | 수치(스테미나 100, 회복 10/s, 경직 3초·면역 10초 등)가 `게임_시스템.pdf`와 같은지 확인. 다르거나 없는 값은 "확인 필요" 목록으로 |
| 화면으로 확인 | 배치안 그림, 벽 투명 처리, 결과창 등은 캡처를 보고 판단 |
| 선택지의 장단점 비교 | 충돌 방식 (가)(나)(다)처럼 장단점과 "나중에 교체할 때 편한가"를 기준으로 선택 |
| 학습 자료 | 이 `Docs/발표대비/` 문서 — 실제 파일·함수 이름 기준으로 구조와 원리를 정리하고, 실습(`08_직접해보기.md`)으로 직접 고쳐 본다 |

## 7. AI 사용의 한계와 주의점 (실제 사례)

AI가 처음에 틀리거나 놓친 것을 **PIE·로그·화면 확인으로 잡은** 사례(자세한 내용은 `03_문제해결_사례.md`):

1. **로그인 크래시**: AI가 쓴 스타일 코드가 지역 변수를 엔진 함수에 넘겼는데, 그 엔진 함수가 주소를 저장하는 동작이라 크래시. 엔진 소스를 읽고 원인을 확정한 뒤 수정.
2. **숨는 곳 카메라**: 첫 수정은 임시 조치였고 근본 해결이 아니었다 → 다시 요청해 전용 카메라로 해결.
3. **배치안 그림**: 첫 결과물의 방 번호가 다른 방에 찍힘 → 직접 열어 검수해서 스크립트 버그를 찾음.
4. **시험 결과 해석**: "오차"로 보인 것이 실제로는 시험 방법 문제(커서가 HUD 위, 카메라 이동 중)였다. 결과를 그대로 믿지 않고 원인을 따져 다시 측정.
5. **예상과 다른 에셋 가져오기 결과**: 충돌 박스가 보이는 벽으로 겹쳐 들어올 거라 예상했지만 실제로는 보이지 않는 충돌로 들어옴 → 가져온 뒤 속성을 읽어 확인하고 진행.
6. **원인을 확정하지 못한 문제**: 빌드 후 DLL "잘못된 이미지" 오류는 해결 순서는 확인됐지만 원인은 "확인 필요"로 남아 있다(모르는 것을 아는 척하지 않기).

**주의점 정리**
- AI는 그럴듯한 설명을 빨리 만든다 → **실행 결과(로그·캡처·테스트)로 확인한 것만 사실로** 취급했다.
- 기획에 없는 부분을 AI가 정하면 **"가정"으로 표시하고 보고서 "확인 필요"에 남기게** 했다(팀이 나중에 확정하도록).
- 되돌리기 어려운 작업(삭제·push·구조 변경)은 **항상 내가 확인 후** 진행했다.
- 서버와 맞춰야 하는 것(`protocol.h`)은 AI가 임의로 고치지 못하게 했다.
