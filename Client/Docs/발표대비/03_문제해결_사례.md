## 1. 로그인 화면 에디터 크래시 — 지역 변수 수명 문제 (2026-10-16)

**증상**
- 메인화면에서 [시작하기]를 눌러 로그인 화면으로 넘어간 **다음 프레임**에 에디터가 꺼짐.
- 오류: `EXCEPTION_ACCESS_VIOLATION`(CoreUObject/SlateCore/Slate). 크래시 로그(Slate.txt)상 **Prepass(위젯 크기 계산)** 중.

**원인을 어떻게 찾았나**
1. "로그인 화면이 처음 뜰 때"만 터진다 → 로그인 화면에만 있는 것: **이름 입력칸(`UEditableTextBox`)**.
2. 입력칸에 스타일을 입히는 공통 코드 `UVHUIStyle::ApplyTextBox`를 의심.
3. 엔진 소스 `EditableTextBox.cpp`(397행 근처)를 직접 읽어 보니, `UEditableTextBox::SetWidgetStyle(InStyle)`이 **자기 안의 복사본이 아니라 넘겨받은 인자 `InStyle`의 주소**를 Slate 위젯에 넘기고 있었다.
4. 우리 코드는 함수 안의 **지역 변수 `Style`** 을 넘겼다 → 함수가 끝나면 그 메모리는 사라짐 → 다음 프레임 Slate가 크기 계산하면서 사라진 메모리의 글꼴 정보를 읽음 → 접근 위반.

**판단 근거**: 크래시 시점(Prepass)·화면(첫 입력칸)·엔진 소스 세 가지가 모두 같은 설명을 가리킴.

**해결** — `Source/MCPTest/UI/VHUIStyle.cpp`, `UVHUIStyle::ApplyTextBox`
```cpp
Box->SetWidgetStyle(Style);                 // Style은 지역 변수 (함수가 끝나면 사라짐)
Box->SetWidgetStyle(Box->GetWidgetStyle()); // 위젯 내부에 복사된 스타일의 주소를 다시 넘김 → 위젯이 살아 있는 동안 유효
```
코드에 왜 이렇게 했는지 주석으로 남겼다(같은 파일 141~144행 주석).

**확인**: 수정 후 로그인·로비·대기실을 반복해 크래시 없음. 커밋 `873f686 로그인 화면 + 에디터 크래시 수정`.

**교훈 (운영체제 수업과 연결)**: 스택에 있는 지역 변수는 함수가 끝나면 무효. 어떤 함수가 **포인터/참조를 "저장"하는지**는 이름만 보고 알 수 없어서 소스를 확인해야 한다(댕글링 포인터). 엔진 디버그 심볼(PDB)이 없어 호출 스택에 함수 이름이 안 나온 것이 어려웠던 점이다.

## 2. 숨는 곳(옷장) 카메라 갇힘 (2026-10-23)

**증상**: 옷장에 숨으면 캐릭터 카메라가 옷장 안에 갇혀 화면이 까맣게 됨. 처음 임시 조치(캐릭터를 옷장 앞에 두기)는 근본 해결이 아니었다.

**원인**: 숨으면 의적을 옷장 안으로 옮기는데, 카메라는 캐릭터에 붙어 있으니 같이 옷장 안으로 들어감.

**해결 (당시, 3인칭 카메라 시절)** — `Gameplay/VHHideSpot.cpp`(생성자에서 `HideCamera` 추가: 옷장 앞 3.8m·높이 2.6m), `Gameplay/VHInteractionSubsystem.cpp`의 `ApplyHide`
- 내 캐릭터가 숨을 때만 `PlayerController::SetViewTargetWithBlend`로 옷장 전용 카메라로 0.35초 부드럽게 전환, 나오면 캐릭터 카메라로 복귀.
- 다른 의적이 숨을 때는 내 화면을 바꾸지 않음.

**확인**: 자동화 테스트 5개 통과 + PIE에서 숨기/나오기 화면 캡처. 커밋 `119e241`.

**그 뒤 변화**: 2026-10-25 탑뷰 카메라로 바뀌면서 카메라가 위에서 내려다보므로 옷장에 갇히지 않는다. 그래서 `AVHHideSpot::bUseHideCamera = false`(기본 꺼짐, `VHHideSpot.h`)로 두고, 블루프린트에서 켜면 예전 방식이 다시 동작하게 남겨 두었다(`VHInteractionSubsystem.cpp` 512행 근처 주석).

**교훈**: 기능을 지우지 않고 옵션으로 남겨 두면 기획이 다시 바뀌어도 되돌리기 쉽다.

## 3. 탑뷰에서 벽에 캐릭터가 가려짐 (2026-10-26)

**증상**: 저택 맵에서 캐릭터가 **화면 아래쪽(카메라 쪽) 벽에 붙으면 완전히 사라짐**. 그 근처의 금고 같은 오브젝트도 가려진다.

**원인을 어떻게 확인했나**
- PIE에서 `S` 키로 아래쪽 벽에 붙인 뒤 화면 캡처 → 캐릭터가 안 보이는 것을 직접 확인(HUD 위치 -58.6m, 벽 -59m).
- 계산: 카메라가 -65°로 내려다보면 높이 3m 벽은 그 뒤 `3 / tan(65°) ≈ 1.4m`의 바닥을 가린다. 캐릭터(약 1.8m)가 벽에 바짝 붙으면 머리까지 가려진다.

**선택지와 결정**: (1) 캐릭터 앞 벽만 투명하게 (2) 카메라를 더 위에서(-80°) (3) 둘 다 (4) 그대로 → **사용자 결정: (1) 캐릭터 앞 벽만 투명하게**.

**해결**
- 재질 `Content/VaultHeist/Materials/M_VHWallFade`: Custom(HLSL) 노드에서 "카메라 → 내 캐릭터" 선을 긋고, 그 선에서 반경 150cm 안이면서 캐릭터보다 카메라 쪽에 있는 벽 픽셀을 지움(경계 40cm는 점무늬).
- 재질 파라미터 모음 `MPC_VHOcclusion`(PlayerPos·Radius·Enabled)에 C++이 매 프레임 캐릭터 위치를 넣음: `Source/MCPTest/Gameplay/VHAimComponent.cpp` `UVHAimComponent::UpdateOcclusion`.
- 바닥 슬롯에는 이 재질을 쓰지 않음(바닥이 사라지지 않게).
- 수치는 `DA_VHGameplayConfig`의 `bWallOcclusionFade`, `OcclusionRadius`.

**확인**: 같은 자리에서 다시 캡처 → 벽에 둥근 구멍이 뚫려 캐릭터가 보임.

**교훈**: 문제를 먼저 화면으로 재현하고 숫자(가려지는 폭)로 설명한 뒤 선택지를 비교했다. 충돌·빛·소리는 그대로 두고 **보이는 것만** 바꿔서 게임 규칙에 영향이 없게 했다.

## 4. 빌드 후 에디터가 "잘못된 이미지" 오류로 안 열림 (2026-10-26)

**증상**: 헤더를 바꿔 에디터를 닫고 빌드(성공)한 뒤 다시 켜자, 로딩 72%에서 "잘못된 이미지" 창 — `UnrealEditor-MCPTest.dll`, 오류 상태 `0xc0e90002`. 로그에는 `Failed to load ... UnrealEditor-MCPTest.dll (GetLastError=4551)`.

**대응**
1. 사용자 판단대로 남은 에디터 프로세스를 모두 종료(확인 결과 0개).
2. 소스는 그대로라 빌드가 "최신 상태"로 건너뛸 수 있어서, `VHAimComponent.cpp`의 수정 시각만 갱신해 **DLL을 다시 링크**(빌드 성공, DLL 시각 갱신 확인).
3. 에디터 재실행 → 로그에서 `InternalLoadLibrary: 'MCPTest'` → `Total Editor Startup Time` 확인 → MCP 연결 확인.

**원인**: **확인 필요.** 빌드 직후 Windows 보안 검사가 새 DLL을 막았거나 파일이 잠겨 있었을 가능성(GetLastError 4551은 "앱 제어 정책이 파일을 차단"을 뜻함). 같은 순서로 해결된다는 것만 확실하다.

**교훈**: 원인을 확정하지 못한 문제는 "해결 순서"와 "확인 방법(로그 줄)"을 남겨 두면 다시 생겼을 때 바로 대응할 수 있다.

## 5. Shift 달리기가 시험에서 인식되지 않음 (2026-10-23~25)

**증상**: 자동 시험 스크립트로 Shift를 누른 채 이동해도 달리기가 안 됨. 직접 키보드로 하면 됨.

**원인**: 시험 스크립트가 Windows API `keybd_event`로 가상 키 코드만 보냈고 **스캔 코드**를 0으로 보냈다. 언리얼은 스캔 코드로 왼쪽/오른쪽 Shift를 구분하는데, 입력 매핑은 **왼쪽 Shift**(`IA_VHSprint`)라서 매칭되지 않았다.

**해결**: 스크립트에서 `MapVirtualKey(vk, 0)`로 스캔 코드를 구해 함께 보냄 → 달리기 600cm/s 확인. (게임 코드 문제가 아니라 **시험 도구** 문제. 스크립트는 작업용 폴더에 있어 저장소에는 없다.)

**교훈**: "기능이 안 된다"와 "시험 방법이 틀렸다"를 구분해야 한다. 사람이 직접 눌러 보는 대조 실험이 결정적 근거였다.

## 6. 공격이 경비원을 못 맞힘 → 범위 규칙 확인 (2026-10-25)

**증상**: 콘솔 `VHSpawnGuard`로 만든 경비원을 좌클릭해도 빗나감.

**원인**: `VHSpawnGuard`는 시선 방향 **정확히 2m 앞**에 경비원을 만든다. 공격 판정 `VHRules::IsInAttackFan`(`Gameplay/VHInteractionRules.cpp`)은 `거리 > 공격 반경(150cm) + 대상 반지름`이면 빗나감 처리. 2m는 범위 밖이다.

**판단**: 코드가 틀린 게 아니라 **규칙대로 동작**한 것. 한 걸음 다가가서 다시 공격 → 경직 확인. 오히려 범위 계산이 맞다는 증거가 됐다.

**관련 코드**: `UVHActionComponent::SweepAttack`(`Gameplay/VHActionComponent.cpp`)이 주변 전투원마다 `IsInAttackFan`을 부르고, 맞으면 판정 담당 `ResolveAttackHit`로 넘긴다.

## 7. Live Coding으로 멤버 변수를 추가할 수 없음 (2026-10-25)

**상황**: 구르기 거리 확인용으로 "구르기 시작 위치"를 저장해야 했는데, 에디터를 켠 채 코드를 바꾸는 **Live Coding**은 클래스에 멤버 변수(헤더 구조)를 추가할 수 없다.

**대응**: 구조를 바꾸지 않고 `.cpp` 파일 안에 파일 범위 변수 `TMap<const UVHActionComponent*, FVector> GRollStartLocations`를 두어 해결(`Gameplay/VHActionComponent.cpp` 30행, 사용은 `RequestRoll`·구르기 끝 로그).

**규칙으로 정리**: `.cpp`만 바꾸면 Live Coding, 헤더·`UCLASS`·`UPROPERTY`를 바꾸면 에디터를 닫고 빌드 후 재실행(CLAUDE.md 빌드 항목). 이 규칙 때문에 오늘도 헤더를 바꿀 때마다 에디터 재시작을 알리고 진행했다.

**한계**: 파일 범위 TMap은 확인용 로그에만 쓰이는 임시방편이다. 정식 기능이라면 멤버 변수로 옮기는 게 맞다(개선 여지).

## 8. 재질 Custom 노드의 입력 배열 설정 실패 (2026-10-25·26)

**증상**: MCP 도구로 `M_VHOutline`, `M_VHWallFade`의 Custom 노드 `Inputs` 배열(입력 핀 이름들)을 한 번에 넣으려 하면 `ArrayAdd: elements changed alongside the size change` 오류.

**원인**: 도구가 "배열 크기 변경"과 "기존 원소 내용 변경"을 한 번에 하면 어디에 끼워 넣을지 모호하다고 거부.

**해결 (M_VHWallFade)**: 현재 배열을 읽어 **똑같은 원소 하나를 덧붙여 크기만 늘리고**, 다음 호출에서 **크기는 그대로 둔 채 새 원소 이름만** 바꾸는 것을 W·C·Pp·R·E 5개까지 반복. 그 뒤 연결·컴파일 성공.

**교훈**: 도구 제약은 "한 번에 하나만 바꾸기"로 우회할 수 있다. 결과는 `get_properties`로 다시 읽어 확인했다.

## 9. 커서 기준 이동 시험의 "오차" 3건 — 시험 방법 문제 (2026-10-26)

**증상**: 커서 6방향 × W/A/S/D 자동 측정에서 ① "위 A/D 로그 없음" ② "아래 W" 31° 오차 ③ "오른쪽위 S" 34° 오차.

**분석**
- ①: 커서 위치(화면 위 25%)가 왼쪽 위 **HUD 패널 위**였다 → 포커스용 클릭이 HUD에 걸려 키 입력이 안 들어감.
- ②③: 로그의 "커서 각도" 자체가 기대값과 달랐다(135°). 카메라가 부드럽게 따라오는(`CameraLagSpeed`) 동안 같은 화면 위치의 커서가 가리키는 **바닥 지점이 움직였기** 때문. 즉 코드는 "커서 기준"으로 정확히 움직였고, 커서가 가리키는 방향이 측정 중 바뀐 것.

**해결**: 커서를 HUD 아래로 옮기고, 매번 0.9초 기다려 카메라가 멈춘 뒤 측정, 그리고 "그 순간의 커서 각도 기준 오차"를 따로 계산 → **두 레벨·손전등 켜짐/꺼짐 84가지 모두 정상**(커서 기준 오차 0~3°).

**근거로 쓴 것**: `AMCPTestCharacter::DoMove`(`Source/MCPTest/MCPTestCharacter.cpp`)에 넣은 확인용 Verbose 로그 `[Move] ... 커서 N° 몸 N° | 이동 방향 | 위치`. 평소엔 숨겨지고 콘솔 `Log LogMCPTest Verbose`로 켠다.

**남긴 기록**: "카메라가 따라오는 동안 방향이 몇 도 흔들릴 수 있다"를 보고서 확인 필요에 적었다(실제 플레이 영향).

## 10. 배치안 그림의 방 번호 오류 (2026-10-26)

**증상**: 팀 공유용 배치안 그림에서 방 번호가 다른 방에 찍히고, 아래 범례 패널의 회색 배경이 왼쪽 일부만 칠해짐.

**원인 (그림을 직접 열어 보고 찾음)**
1. PowerShell에서 `(PX $a + PX $b) / 2`처럼 쓰면 `PX` 함수가 `$a`, `+`, `PX`, `$b`를 **전부 인자로** 받아 계산이 틀어짐 → `((PX $a) + (PX $b)) / 2`로 괄호를 넣어야 함.
2. PowerShell 변수 이름은 **대소문자를 구분하지 않아** 방 너비 `$w`가 그림 너비 `$W`를 덮어씀 → 변수 이름을 `$rw`·`$rh`로 바꿈.

**해결 위치**: `Tools/MapOverlay/draw_final.ps1`. 이후 "큰 홀" 글자와 시작 표시 겹침, 탈출구 바닥판이 축 눈금 "-45"를 가리는 것도 고치고 부분 확대 이미지로 다시 확인.

**교훈**: 결과물을 "만들었다"로 끝내지 않고 **직접 열어서 검수**했기 때문에 공유 전에 잡았다.

## 11. 문이 하나도 없는 방 3곳 발견 (2026-10-26)

**상황**: 모델러 블록아웃의 벽 98개 좌표를 평면도 좌표로 표로 만들어 방을 나누다가, 지역 11·13·20번은 사방이 막혀 **들어갈 수 없는** 방임을 발견. 렌더 메시가 충돌 박스와 같은 상자 98개(삼각형 1,176 = 98 × 12)라 메시에도 문이 없다고 판단.

**대응**: 지역은 만들되 `AVHRoomVolume::bAllowReturnPoint = false`, 이름에 "(문 없음)" → 반납지점은 30곳에서만 나온다(로그 `방 30개`로 확인). 보고서 "모델러 요청 사항"에 좌표와 함께 정리.

## 12. VHGoto 뒤 반납이 안 됨 → 시선 = 커서 (2026-10-26)

**증상**: 콘솔 `VHGoto ReturnPoint`로 이동 후 G를 눌러도 반납이 안 됨.

**원인**: 탑뷰라 시선이 **마우스 커서 방향**이고, 커서가 반납지점 반대쪽에 있었다(화면 캡처에서 손전등이 오른쪽을 비춤). 그사이 반납지점이 60초가 되어 사라지기도 했다(교체 규칙이 정상 동작한다는 확인도 됨).

**해결**: 커서를 반납지점 쪽에 두고 다시 눌러 반납 성공(`반납: 보물 1개 2400$ → 합계 2400 / 10000$`). 가이드에 "VHGoto 뒤에는 커서를 오브젝트 쪽에" 안내 추가.

| 로비에서 [빠른 찾기]를 너무 빨리 눌러 무시됨 | 목록을 받은 뒤 다시 클릭 |

| 로그인 화면마다 `Attempting to focus Non-Focusable widget` 경고 | 동작 영향 없음, 남은 문제로 기록(10-16 보고서) |

## 공통으로 쓴 문제 해결 방법 (발표 때 이 순서로 말하기)

1. **재현**: PIE에서 같은 상황을 다시 만든다(콘솔 명령 `VHGoto`, `VHSetTime`, `VHStunSelf` 등으로 빠르게).
2. **관찰**: 출력 로그(`[Interact]`, `[Match]`, `[Move]`, `[Attack]` 등 태그), 화면 캡처, 엔진 소스.
3. **가설 → 확인**: "이게 원인이면 이렇게 되어야 한다"를 하나씩 확인(예: 2m는 범위 밖인지 계산).
4. **최소 수정**: 원인 위치만 고치고, 왜 그렇게 했는지 주석·보고서에 남긴다.
5. **재확인**: 같은 방법으로 다시 확인 + 자동화 테스트 + 커밋.
6. **시험 도구도 의심**: 5·9·12번처럼 "코드가 아니라 시험 방법"이 문제인 경우가 꽤 있었다.
