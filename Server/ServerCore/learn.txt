 SOLID 원칙
 분리의 기준: 
 1. S: 단일 책임 원칙 (Single Responsibility Principle) (하나의 클래스는 하나의 일만 한다)
 2. O: 개방-폐쇄 원칙 (Open/Closed Principle) "기능 확장에는 열려(Open) 있어야 하고, 코드 수정에는 닫혀(Closed) 있어야 한다."
 3. L: 리스코프 치환 원칙 (Liskov Substitution Principle) "부모 클래스가 들어갈 자리에 자식 클래스를 대신 넣어도 코드가 완벽하게 작동해야 한다."
 4. I: 인터페이스 분리 원칙 (Interface Segregation Principle) "자신이 사용하지 않는 기능(함수)에 억지로 의존하게 만들지 마라."
 5. D: 의존성 역전 원칙 (Dependency Inversion Principle)"구체적인 알맹이(자식)가 아니라, 추상적인 껍데기(부모/인터페이스)에 의존해야 한다."

 1. SendBuffer는 왜 만들었을까?
 메모리 청크(Chunk) 재활용: 매번 새로 만들지 않고, 
 미리 커다란 메모리 공간(예: 64KB)을 통째로 할당해 둔 뒤(SendBufferChunk), 
 패킷을 보낼 때마다 그 공간의 일부 조각(Offset)을 잘라서 사용하기 위해

 안전한 수명 보장 (SendBufferRef): 앞서 보셨듯, 윈도우가 비동기로 데이터를 다 보낼 때까지 이 메모리가 절대 사라지면 안 됩니다. 
 SendBuffer를 스마트 포인터로 감싸두면, 전송이 끝날 때까지 메모리가 안전하게 유지되다가 일이 끝나면 알아서 회수됩니다

 2. 모아 쏜 것(WSASend의 WSABUF 배열)은 어떻게 관리되나

보낼 때 (Send / 모아 쏘기):
게임 로직에서 A 패킷, B 패킷, C 패킷을 보내려고 합니다. 이때 각각을 따로 보내지 않고, 
SendBuffer에 차곡차곡 연달아 적은 뒤(또는 각각의 SendBufferRef를 모아서), 
WSABUF 배열에 그 주소들을 꽂아 넣고 WSASend로 한 번에 던집

받을 때 (Recv / 패킷 프레이밍):
이렇게 모아 쏘거나 TCP 스트림을 통해 데이터가 상대방에게 도착하면, 
상대방은 그냥 줄줄이 이어진 거대한 바이트 덩어리(Stream)로 받게 됩니다.
상대방의 RecvBuffer는 이 덩어리를 받아서, 패킷 맨 앞에 붙어있는 '크기(Size) 정보'를 보고 
"아, 여기서부터 여기까지가 A 패킷이구나, 그다음부터는 B 패킷이구나!" 하고 칼로 무 베듯 잘라내는 작업(패킷 프레이밍)을 거칩니다.

타임아웃을 통해 운영체제에게 "일이 없으면 이 시간 동안은 CPU를 다른 곳에 양보하고 쉴게"라고 선언하는 거야.

extern과 분업: 이를 막기 위해 헤더 파일에는 extern 키워드를 붙여 
"이 변수는 어딘가에 존재한다"라고 선언만 알려줘. 
그리고 실제 변수를 0이나 빈 배열로 초기화하여 메모리에 만드는 작업(정의)은

프로그램 전체의 코드 구조상으로는 오직 하나의 원본 정의를 가져야 해. 런타임에는 
스레드마다 따로 존재하더라도 컴파일 타임에는 반드시 단 한 번만 정의되어야 하므로 .cpp 파일로 분리하는 것이 필수적이야.

코드 조각이 하는 일 (매개변수 해석):
Ret (T::*memberFn)(Args...): "어떤 클래스 T의 멤버 함수 주소"야 (예: &GameRoom::Enter).   
Params&&... params: 그 함수를 실행할 때 넘겨줄 인자들 (예: player).   
안쪽의 Bind<T> 함수가 이 둘을 받아서 "아, 이 객체의 이 멤버 함수에 이 인자를 넣어서 실행하는 람다 포장지"를 내부적으로 뚝딱 만들어 준 뒤, 
기본 버전인 Push로 넘겨주는 거지.

// Actor 방식의 공유 상태 보호.
//
// 객체(Lobby, GameRoom …)가 JobQueue를 상속하면, 그 객체의 상태를 바꾸는 일은 모두 Job으로 넣는다.
//   room->DoAsync(&GameRoom::Enter, player);
// 한 JobQueue의 Job은 "한 번에 한 스레드만, 넣은 순서대로" 실행된다. 그래서 GameRoom 안의 멤버는
// 락 없이 그냥 읽고 써도 된다. 여러 스레드가 동시에 DoAsync해도 실행은 줄을 선다.
//
// 누가 실행하나: 큐가 비어 있을 때(0 → 1) Job을 넣은 스레드가 "실행 담당"이 되어 큐가 빌 때까지 실행한다.
// 이미 누가 실행 중이면 넣기만 하고 돌아간다. 실행 담당이 시간 예산을 넘기면 GlobalQueue에 넘기고
// 다른 Worker가 이어서 실행한다.
