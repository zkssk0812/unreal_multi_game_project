# 「털어라! 금고!」 서버 개발 문서

- 기준 기획서: `기획서(수정안)` (최근 편집본)
- 대상: 졸업작품 시연 (방 하나에 최대 3명, 동시 방 수십 개 정도)
- 목표일: **2026-10-28** — 완벽하지 않아도 서버의 모든 기능이 동작하고, 가능한 범위에서 최적화
- 진행 상황과 일정: [ROADMAP.md](../ROADMAP.md)

## 1. 서버가 할 일 한눈에 보기

| 기획서 | 서버가 하는 일 |
|---|---|
| 메인 화면, 게임 시작 | 접속, 닉네임으로 입장(로그인) |
| 방 만들기 / 방 참여 | 방 목록, 생성, 참여(최대 3명), 나가기 |
| 준비 단계 | 캐릭터 선택(중복 불가), 퍽 선택(최대 3개, 중복 가능), 준비, 전원 준비 시 시작 |
| 게임 플레이 단계 (5분) | 로딩 동기화, 20Hz 틱, 이동 동기화, 금고·보물·반납·탈출, 공격·회피·스테미나, 포획·창고·구출, 은신, 경비원 AI, 승패 판정 |
| 플레이 결과 출력 | 플레이어별 결과·점수 전송, 메인 화면으로 복귀 |

**서버 권위(authority) 원칙**

- 게임 규칙의 결과(금고가 열렸나, 보물이 누구 것인가, 잡혔나, 이겼나)는 **서버만** 정합니다. 클라는 요청만 보냅니다.
- 이동은 클라가 정한 위치를 서버가 **그대로 받아** 다른 사람에게 전달합니다(검증·보정 없음). 3인 PvE 졸작이라 부정행위 방지는 다루지 않습니다.
- 경비원(NPC)은 서버에서만 움직이고, 클라는 받은 위치를 그립니다.

## 2. 전체 구조

```
┌──────────────────────────────────────────────────────────────┐
│ GameServer (exe)                                              │
│  main.cpp  : 조립 (코어 시작 → 콘텐츠 시작 → 접속 받기)        │
│  Net/      : GameSession, PacketHandler(표·단계 검사),          │
│              Heartbeat, Handlers/                              │
│  Protocol/ : CommandDecoder (패킷 → Cmd), MessageEncoder (Msg → 패킷) │  ← 브리지
├──────────────────────────────────────────────────────────────┤
│ VaultHeistContent (lib)  : 게임 규칙. 소켓·패킷을 모른다        │
│  Interface/ : IClientChannel, IMessageEncoder, ILobbyApi, IRoomEndpoint │
│  Messages/  : Cmd(받는 명령), Msg(보내는 메시지), Types         │
│  Lobby/, Room/, Game/ (Phase 2~5에서 추가)                     │
├──────────────────────────────────────────────────────────────┤
│ ServerCore (lib) : IOCP, Session, SendBuffer, 메모리 풀, JobQueue, JobTimer, Logger │
├──────────────────────────────────────────────────────────────┤
│ Common/Protocol (저장소 루트) : protocol.h (클라와 공유)              │
│ Shared/Protocol : protocol.h (Common과 같은 사본), PacketBuilder, ProtocolUtil │
└──────────────────────────────────────────────────────────────┘
```

- **브리지**는 패킷과 게임 규칙 사이의 통역입니다. 콘텐츠는 `protocol.h`를 include하지 않고, 브리지가 `Cmd`/`Msg` 구조체로 바꿔 줍니다. 그래서 콘텐츠는 서버 없이 `ContentTests`로 시험할 수 있습니다.
- **스레드**: IOCP Worker N개(코어 수)가 네트워크 완료 → JobTimer 분배 → GlobalQueue 실행을 반복합니다. 별도 게임 스레드는 없습니다.
- **직렬화**: 로비 하나, 방(GameRoom)마다 하나씩 `JobQueue`를 상속합니다. 같은 방의 일은 한 번에 한 스레드만 실행하므로 방 안의 상태는 **락 없이** 다룹니다.
- **시간**: 방의 틱, 로딩 제한, 결과 화면 타이머는 모두 `JobTimer`(DoTimer)로 예약합니다. `timeBeginPeriod(1)`로 1ms 정밀도.

## 3. 연결 단계

```
접속 ─ Anonymous ─CS_LOGIN→ Authenticating ─성공→ Lobby ─방 생성/참여→ Room ─전원 준비→ Game
                       ↑        실패(Anonymous로)            ↑ 나가기        결과 후 복귀 → Lobby
```

| 단계 | 허용 패킷 (CS_PING은 항상 허용) |
|---|---|
| Anonymous | CS_LOGIN |
| Authenticating | 없음 (CS_LOGIN 재전송은 조용히 버림) |
| Lobby | CS_ROOM_LIST, CS_CREATE_ROOM, CS_JOIN_ROOM |
| Room | CS_LEAVE_ROOM, CS_SELECT_CHARACTER, CS_SELECT_PERKS, CS_READY |
| Game | CS_LOAD_COMPLETE, CS_MOVE, CS_ACTION, CS_RETURN |

- 허용되지 않은 패킷 → `SC_KICK(ProtocolViolation)` 후 끊음. 단, 단계가 바뀐 지 1초 이내의 CS_MOVE·CS_ACTION은 늦게 도착한 것으로 보고 버립니다.
- 등록되지 않은 패킷 id → 응답 없이 끊음.
- 단계는 콘텐츠(로비·방)가 `SetPhase`로 바꾸고, `CS_LOGIN`을 받은 순간의 Authenticating만 브리지가 바꿉니다.

**하트비트** (`GameServer/Net/Heartbeat`)

- 10초 동안 아무 패킷도 없으면 끊습니다. 클라는 2초마다 CS_PING을 보냅니다.
- 클라가 비정상으로 사라진 경우(전원 차단 등)와 SC_KICK 뒤에 닫지 않는 경우를 정리합니다.
- 해킹 방지용 규칙(전송 빈도 제한, 로그인 제한 시간 등)은 두지 않습니다.

---|---|---|
| 하트비트 | 10초 동안 아무 패킷도 없음 | 끊음 (클라는 2초마다 CS_PING) |
| 로그인 제한 | 접속 후 30초 안에 로그인 안 함 | 끊음 |
| 끊는 중 제한 | SC_KICK 후 3초 안에 상대가 안 닫음 | 강제로 끊음 |
| 종류별 빈도 (초당) | 이동 30, 행동 20, 핑 2, 그 밖의 요청 10 | 넘은 것만 버림 |
| 전체 빈도 | 초당 100개를 3초 연속 넘음 | SC_KICK(RateLimit) |

## 4. 프로토콜 v2

`Common/Protocol/protocol.h`(저장소 루트)가 정본입니다. 여기에는 구성만 적습니다.

- 모든 패킷: `[size:uint16][type:uint16][body]`, 리틀 엔디언, `#pragma pack(1)` 고정 구조체.
- 가변 길이 패킷은 배열이 마지막 멤버이고 `count`개만 보냅니다(`*_Size(count)`로 크기 계산).
- 문자열 UTF-8 널 종료, **좌표 cm 3D(x, y, z, UE 기준 Z-up)**, 각도 도(degree), 시간 ms.
- 버전 `PROTOCOL_VERSION`이 정확히 같아야 접속(다르면 SC_LOGIN(VersionMismatch) 후 끊음).

| 대역 | 패킷 |
|---|---|
| 1000 입장 | CS_LOGIN / SC_LOGIN |
| 2000 로비·방 | CS_ROOM_LIST / SC_ROOM_LIST, CS_CREATE_ROOM / SC_CREATE_ROOM, CS_JOIN_ROOM / SC_JOIN_ROOM, CS_LEAVE_ROOM / SC_LEAVE_ROOM, SC_ROOM_STATE, CS_SELECT_CHARACTER, CS_SELECT_PERKS, CS_READY, SC_ROOM_ERROR |
| 3000 게임 진행 | SC_GAME_LOAD, CS_LOAD_COMPLETE, SC_GAME_START, CS_MOVE, SC_SNAPSHOT, CS_ACTION, SC_ACTION_REJECT, SC_ENTITY_SPAWN, SC_ENTITY_DESPAWN, SC_GAME_END, CS_RETURN |
| 4000 게임 이벤트 | SC_ATTACK, SC_HIT, SC_CAPTURED, SC_RELEASED, SC_JAILED, SC_INTERACT, SC_SAFE_OPENED, SC_TREASURE, SC_ESCAPED, SC_HIDE, SC_GUARD_ALERT |
| 9000 시스템 | CS_PING / SC_PONG, SC_KICK, SC_NOTICE |

**방 안 요청의 응답 규칙**: 캐릭터·퍽·준비 요청은 개별 성공 응답이 없습니다. 성공하면 방 전원에게 `SC_ROOM_STATE`, 실패하면 요청자에게만 `SC_ROOM_ERROR`.

**같은 틱의 순서**: 그 틱에 생긴 이벤트(4000번대)를 먼저 보내고, 그 틱의 `SC_SNAPSHOT`을 나중에 보냅니다.

## 5. 로비와 방

| 항목 | 규칙 |
|---|---|
| 닉네임 | 1~12자(UTF-8 48바이트 이하), 앞뒤 공백 제거, 접속 중인 사람과 중복 불가. 계정·비밀번호·DB 없음 |
| 플레이어 ID | 로그인 성공 시 서버가 1부터 발급. 접속이 끊기면 사라짐 |
| 방 생성 | 방 이름 1~20자. 만든 사람이 방장. 생성 즉시 그 방에 들어감 |
| 방 인원 | 방장 포함 최대 3명 |
| 방 목록 | 대기 중(Waiting)인 방만, 최대 20개 |
| 방장 이탈 | 남은 사람 중 먼저 들어온 사람이 방장. 아무도 없으면 방 삭제 |
| 캐릭터 | 방 안에서 중복 불가. ID는 1~4 (기획 확정 전 임시) |
| 퍽 | 0~3개, 한 사람 안에서는 서로 달라야 함, 다른 사람과는 중복 가능. ID는 1~8 (임시) |
| 준비 | 캐릭터를 골라야 준비 가능. 준비 중에 캐릭터·퍽을 바꾸면 준비 해제 |
| 시작 | 방 안의 전원이 준비 → 로딩 시작 (1명이어도 시작 가능: 시연·시험용) |
| 결과 후 | 기획서 흐름대로 **메인 화면(Lobby 단계)으로 복귀**하고 방은 사라짐 |
| 로딩·게임 중 이탈 | 나가기는 없음(클라 단계가 Game이라 CS_LEAVE_ROOM이 막힘). 접속이 끊기면 의적을 "이탈"로 표시하고 결과에 포함. 모두 끊기면 판 중단 |

### 5.1 로비와 방의 역할 나눔 (P2 구현)

| | GameLobby (서버에 하나) | GameRoom (방마다 하나) |
|---|---|---|
| 주인인 상태 | 닉네임, 플레이어 ID, **누가 어느 방에 있나**(정원 판단), 방 목록 | 방 안의 캐릭터·퍽·준비, 방 상태(Waiting/Loading) |
| 받는 패킷 | CS_LOGIN, CS_ROOM_LIST, CS_CREATE_ROOM, CS_JOIN_ROOM | CS_LEAVE_ROOM, CS_SELECT_CHARACTER, CS_SELECT_PERKS, CS_READY (브리지가 방으로 바로 넣음) |
| 보내는 패킷 | SC_LOGIN, SC_ROOM_LIST, 실패한 SC_CREATE_ROOM·SC_JOIN_ROOM | 성공한 SC_CREATE_ROOM·SC_JOIN_ROOM, SC_ROOM_STATE, SC_ROOM_ERROR, SC_LEAVE_ROOM |

- 둘 다 JobQueue이고 서로의 멤버를 직접 만지지 않습니다. 로비 → 방: `Enter`, `Disconnected`. 방 → 로비: `MemberLeft`, `RoomStateChanged`.
- **입장**: 로비가 정원·상태를 보고 명단에 넣은 뒤 방에 `Enter`를 보냅니다. 방은 마지막으로 한 번 더 확인하고(그 사이 Loading이 됐을 수 있음) BindRoom → SetPhase(Room) → 응답 순서로 처리합니다.
- **나가기**: 방이 멤버를 지우고 BindRoom 해제 → SetPhase(Lobby) → 로비에 `MemberLeft` → SC_LEAVE_ROOM 순서. 로비에 먼저 알리므로 클라가 곧바로 방을 만들어도 AlreadyInRoom이 되지 않습니다.
- **접속 종료**: 로비가 명단에서 바로 빼고 방에는 `Disconnected`로 알립니다. 로그인 응답 전에 끊긴 연결도 채널 ID로 찾아 닉네임을 풀어 줍니다.
- **방장**: 두 쪽 모두 "들어온 순서의 맨 앞"을 방장으로 봅니다(로비가 넣은 순서대로 방에 들어가므로 순서가 같음).

## 6. 게임 플레이

### 6.1 진행 순서

1. **로딩**: 방이 `SC_GAME_LOAD`(맵, 금고 위치, 스폰 배정)를 보냄 → 클라가 다 읽으면 `CS_LOAD_COMPLETE`. 30초가 지나면 기다리지 않고 시작(로딩이 덜 된 사람도 SC_GAME_START를 받고 따라 들어옴). 로딩 중 끊긴 사람은 이탈 처리.
2. **시작**: `SC_GAME_START`(시작 시각, 5분, 모든 엔티티) → 20Hz 틱 시작.
3. **진행**: 틱마다 입력 반영 → 규칙 판정 → 경비원 AI → 이벤트 전송 → 스냅샷 전송.
4. **종료**: 승패 조건 만족 또는 5분 경과 → `SC_GAME_END`(결과) → 15초 뒤(또는 CS_RETURN) Lobby로 복귀.

### 6.1.1 구현 구조 (P3)

| 파일 | 역할 |
|---|---|
| `Content/Game/MapData` | 맵 데이터(스폰, 금고 후보 10곳, 방(반납 지점 후보), 탈출구, 창고, 숨는 곳, 순찰 지점, 충돌체, 경로 격자). 서버 시작 때 `Data/Maps/mansion_1f_server.json`을 읽어(`MapLoader.cpp`, nlohmann/json) 한 번 채우고 모든 방이 읽기 전용으로 공유. 경로 격자는 서버가 충돌체로 직접 만듦 |
| `Content/Game/GameWorld` | 엔티티 목록, 입력 반영, 스테미나, 스냅샷·결과 만들기. JobQueue가 아닌 평범한 클래스(방의 Job 안에서만 씀). P4부터 규칙 판정(6.5)도 여기서 |
| `Content/Room/GameRoomPlay.cpp` | GameRoom의 게임 진행 부분: 로딩 → 시작 → 틱 → 종료 → 결과 → 복귀 |

- 시간이 걸리는 일(로딩 제한, 다음 틱, 결과 화면)은 모두 `DoTimer`로 방의 Job을 예약합니다. 예약에는 **판 번호(matchId)**를 넣어, 판이 바뀐 뒤 늦게 실행되는 예약은 아무것도 하지 않습니다.
- 다음 틱은 "지금부터 50ms 뒤"가 아니라 "시작 시각 + (틱 번호 + 1) × 50ms"로 예약해 처리 시간만큼의 밀림이 쌓이지 않게 합니다.
- 입력 수신함(`_inbox`)만 락으로 지킵니다. IOCP Worker는 `push_back`만 하고, 틱이 `swap`으로 통째로 가져갑니다.
- 게임 시간은 `GameData::CurrentTiming()`(틱 50ms, 게임 5분, 로딩 30초, 결과 15초)으로 정하며, ContentTests만 짧게 바꿉니다.

### 6.1.2 규칙 구현 구조 (P4)

- **GameWorld가 판정하고 방은 보내기만** 합니다. 그 틱에 생긴 일(공격, 포획, 금고 열림…)은 GameWorld가 `_events`(`WorldEvent` = 이벤트 메시지들의 `std::variant`)에 쌓고, 방의 틱이 `TakeEvents()`로 꺼내 `std::visit`으로 알맞은 `Encode`를 골라 보냅니다.
- 틱 순서: ① 입력 반영(공격·상호작용 *시작*) → ② `Update`(스테미나, 상호작용 진행·완료, 공격 판정, 회피 무적, 운반, 경직·무적 해제, 탈출) → ③ 이벤트 전송 → ④ 스냅샷 → ⑤ `CheckEnd`/5분.
- 게임 안 시간은 `GameWorld::_nowMs`(Update로만 흐름)로 잽니다. 공격의 선딜·판정·후딜도 "시작 시각 + 경과"로 계산하므로 시험에서 시간을 마음대로 흘릴 수 있습니다.
- 경비원이 기절하며 떨어뜨리는 보물은 엔티티를 순회하는 도중에 만들면 `vector` 재할당으로 참조가 깨지므로, 모았다가 순회가 끝난 뒤 만듭니다(`_pendingDrops`).
- 경비원의 공격·감금은 `GuardAttack` / `JailCarried`로 열어 두고, P5 AI가 부릅니다(지금은 시험이 직접 부름).
- 값(시간·거리·스테미나·점수)은 모두 `Content/GameData.h`에 있습니다.

### 6.2 틱과 동기화

| 항목 | 값 |
|---|---|
| 서버 틱 | 20Hz (50ms) |
| 스냅샷 | 매 틱 방 전원에게 같은 패킷 하나 (패킷을 한 번 만들고 공유) |
| 클라 이동 전송 | 최대 20Hz. 멈춰 있으면 보내지 않되 1초에 한 번은 보냄 |
| 이동 | 클라가 보낸 위치·방향·달리기 상태를 그대로 반영 (검증 없음) |

방 안 3명 + 경비원 3명 + 오브젝트 수십 개라, 시야 제한(AOI) 없이 전원에게 같은 스냅샷을 보내도 충분합니다.

### 6.3 엔티티

### 6.5 규칙

> 클라 게임 시스템(「클라이언트_게임시스템.md」·「게임_시스템.pdf」)을 따릅니다. 바꾼 내용은 [RULES_CHANGE_PLAN.md](RULES_CHANGE_PLAN.md).

**금고**
- 후보 10곳 중 5곳에 무작위 배치. 금고 하나에 보물 1개(10종 중 서로 다른 종류).
- 상호작용을 **30초** 유지하면 열림. 중간에 멈추면 진행도 유지, 다시 하면 이어서.
- 한 번에 한 명만 상호작용 가능. 열린 금고 안의 보물을 상호작용으로 줍습니다.

**보물**
- 10종, 종류마다 무게·가치(`GameData::TreasureTypes`, 클라 값을 받기 전 임시값). 한 명당 **최대 10개·20kg**, 넘게 되는 줍기는 거절(TreasureFull / TooHeavy).
- 보물을 들면 소리 반경이 커집니다((기본 + 개당 2m) × 1.1). 무게에 비례해 달리기·공격·구르기 스테미나가 1배(0kg) → 2배(20kg).
- 경비원에게 잡히면 가진 보물이 종류 그대로 그 경비원 것이 됩니다. 경비원이 기절하면 가진 보물을 모두 주위에 떨어뜨립니다.

**반납 지점과 탈출**
- 반납 지점은 항상 3곳, 방마다 최대 1개. 방 안의 걸을 수 있고 의적이 닿는 칸 중 무작위(문 없는 방·창고 제외).
- 구역 안에서 4초 머물면(한 명씩, 끊기면 처음부터, 2초 이하 남은 구역은 시작 불가, 도중에 닫히면 실패) 가진 것을 모두 반납하고, 그 지점은 사라져 다른 방에 새로 생깁니다(사라진 방·이미 있는 방 제외). 25초가 지나면 빨강(Warning, 마지막 5초), 30초면 같은 방식으로 교체.
- 팀 반납 **가치**가 **10,000$**가 되는 순간 탈출구가 저절로 열리고 전원에게 SC_EXIT_OPENED. 탈출구에 상호작용하면 NotAvailable.
- 탈출구가 열린 뒤 **탈출 구역**(맵 파일의 `exit.escape_zone`)에 들어선 의적은 탈출합니다. 들고 있던 보물도 반납으로 칩니다.

**상호작용 공통** (P4 구현)
- 상호작용 위치(`interact_pos`)에서 150cm 안(바닥 위 거리)이어야 합니다. 반납 지점은 가운데에서 100cm.
- 즉시: 열린 금고에서 보물 줍기, 떨어진 보물 줍기. 반납은 4초. 시간: 금고 30초(진행도 유지), 구출 5초, 숨기 1초(처음부터).
- 시간 걸리는 상호작용은 대상마다 한 명(TargetBusy). 범위를 벗어나거나, 공격·구르기하거나, 잡히면 중단(SC_INTERACT Cancel).
- 공격·구르기가 끝나기 전에는 상호작용을 시작할 수 없습니다.

**공격과 구르기**

| | 의적 | 경비원 |
|---|---|---|
| 걷기 / 뛰기 | 3 / 6 m/s (뛰기는 스테미나 10/s) | 3 / 6 m/s |
| 스테미나 | 100, 초당 10 회복, 0이면 탈진(100까지 특수 동작 불가, 회복 50%) | 없음 |
| 공격 | 선딜 0.2 / 판정 0.5 / 후딜 0.3초, 스테미나 30 | 선딜 0.2 / 판정 0.35 / 후딜 0.45초 |
| 공격 범위 | 시선 방향 120° 부채꼴, 거리 0.5m (캐릭터 크기 기준, 맵 크기에 맞춰 조정) | 같음 |

- 의적이 경비원을 맞히면: 경비원 **경직 3초**, 붙잡고 있던 의적 풀려남, 가진 보물 떨어뜨림. 경직이 끝나면 **10초 면역**.
- 경비원이 의적을 맞히면: 의적 **포획**, 가진 보물 이동, 경비원이 창고로 운반.
- 판정: 판정 구간 동안 매 틱 검사, 한 공격은 한 명만 맞힘. 거리 120cm, 시작할 때 방향 기준 좌우 60°, 높이 차 150cm 이하(3D).
- 구르기: 누르는 순간부터 0.5초 동안 무적(Dodging 비트), 스테미나 20. 숨어 있는 의적도 공격에 맞지 않습니다.
- 앞 공격·구르기가 끝나기 전에 다시 하면 Cooldown, 스테미나가 모자라거나 탈진이면 NoStamina.
- 공격 소리: 빗나가면 5m, 맞히면 20m (한 번).

**창고와 구출**
- 창고에 갇힌 의적은 스스로 나올 수 없습니다. 밖의 의적이 창고 문과 상호작용하면 갇힌 전원이 풀려납니다.

**은신**
- 숨는 곳과 상호작용이 끝나면 은신 상태. 은신 중에는 경비원 시야에 걸리지 않습니다. 다시 상호작용하면 나옴.
- 경비원이 의적이 숨는 것을 봤다면 그 숨는 곳을 열어 끄집어냅니다(포획).

**승패** (개인별)
- 탈출한 의적은 승리, 못 한 의적은 패배.
- 게임 종료 조건: 모든 의적이 탈출했거나 갇힘 / 남은 의적이 모두 갇힘 / 5분 경과.

**점수** (결과 화면용, 서버 임시 공식)
- 탈출 1000 + 반납 가치 ÷ 10 + 연 금고 × 100 + 경비원 기절 × 50

## 7. 경비원 AI

### 7.1 상태

```
순찰 ──소리──→ 의심 ──도착·못 찾음──→ 주변 탐색 ──없음──→ 순찰
 │              │                        │
 └──시야에 의적──┴──────────→ 추격 ──공격 범위──→ 공격 ──성공──→ 포획 → 창고 이동 → (가둠) → 순찰
                               │ 놓침(3초)           └실패: 0.5초 경직 후 추격
                               └────────→ 주변 탐색
 의적에게 맞음 → 경직(기절) → 주변 탐색
```

| 상태 | 행동 |
|---|---|
| 순찰 | 순찰 지점을 따라 걷기. 갈림길에서 1초 둘러본 뒤 무작위 방향 |
| 의심 | 들은 소리 위치로 걸어감. 도착할 때까지 못 찾으면 주변 탐색 |
| 추격 | 달려서 의적을 쫓음. 시야에서 3초 벗어나면 놓침 → 주변 탐색 |
| 공격 | 선딜 → 판정 → 후딜. 실패 시 0.5초 경직 |
| 포획 / 창고 이동 | 잡은 의적을 들고 창고까지 최단 경로. 잡은 수만큼 느려짐. 도중에 의적을 보면 추격(들고 있는 채로) |
| 경직 | 아무것도 못 함. 잡고 있던 의적과 보물을 놓음 |
| 주변 탐색 | 제자리에서 둘러봄(2초). 의적이 보이면 추격, 보물만 보이면 주우러 감, 없으면 순찰 |

### 7.2 감지

- **시야**: 경비원의 손전등 범위(시선 방향 부채꼴)를 시야로 봅니다. 기획서 회의록의 방식대로 ① 부채꼴 안에 있고 ② 경비원과 의적 사이에 벽이 없으면 발견. 거리·각도는 3D 좌표로 판정합니다. 은신 중이면 발견 안 됨.
- **추격 대상 선택**: "누가 먼저 들어왔나"는 쓰지 않습니다(기획서: 무조건 배제). 시야 안의 의적 중 **가장 가까운** 의적.
- **소리** (클라 소리 표): 걷기 0m, 달리기 12m·0.2초마다, 구르기 15m·구르는 동안 매 틱, 공격 빗나감 5m·적중 20m. 보물을 들면 (기본 + 개당 2m) × 1.1, 기본이 0이면 소리 없음. 반경 안의 경비원이 들으면 의심 상태.

### 7.3 맵과 경로

- 맵 데이터는 **`Data/Maps/mansion_1f_server.json`**(저택 1층, `mansion_1f` v1)이고, `tools/fbx_to_map.py`가 만듭니다. **벽·바닥은 블록아웃 메시 `Data/Maps/Mansion_1F_Blockout.fbx`**(언리얼 충돌 박스 `UCX_` 98개 = 벽 93 + 바닥판 5)에서, **게임 지점(스폰·금고·숨는 곳·방·탈출구·창고·순찰)과 소품 충돌체(옷장·금고·문)**는 클라 팀 데이터에서 가져와 합칩니다(FBX에는 게임 지점이 없음). FBX는 X축을 뒤집어 저장하므로(`CoordAxisSign = −1`) 언리얼 좌표 = (−x, y, z). 맵이 바뀌면 FBX를 교체하고 `python tools/fbx_to_map.py` → 서버 재시작. 좌표는 Unreal 월드 좌표(cm, X = 위쪽(북), Y = 오른쪽(동), Z = 위)로 서버와 같습니다.
- 서버는 **시작할 때 한 번** 이 JSON을 읽어 `MapData` 하나를 채우고 서버가 꺼질 때까지 메모리에 둡니다(`Content/Game/MapLoader.cpp`, JSON 파서는 `ThirdParty/nlohmann/json.hpp`). 모든 방은 `const MapData&`로 읽기만 하므로 복사도 락도 없습니다.
- 빌드하면 `Data/Maps/*.json`이 실행 파일 옆(`Binaries/x64/<구성>/Data/Maps`)으로 복사되고, 서버는 실행 파일 위치 기준으로 찾습니다(작업 폴더와 무관). 맵이 바뀌면 파일만 교체하고 서버를 다시 켜면 됩니다.
- 읽은 뒤 규칙을 검사합니다(`ValidateMap`: 의적 스폰 3곳 이상, 금고 후보 5곳 이상, 스폰·금고 상호작용 위치가 이동 가능한 칸 등). 파일이 없거나 형식·규칙이 틀리면 이유를 로그로 남기고 **서버를 시작하지 않습니다**.
- 들어 있는 것: 스폰(의적 3, 경비원 3), 금고 후보 10곳(+상호작용 위치), 숨는 곳 8, 방 33(반납 지점 후보, `vents`는 옛 규칙이라 읽지 않음), 탈출구와 탈출 구역, 창고 문·감금 자리 3·창고 구역, 순찰 지점 47개와 연결 68개, 충돌체 114개(정적 102 + 있다 없다 하는 것 12: 금고 10·창고 문·탈출구), 경로 격자의 틀(50cm × 196행 × 138열).
- **경로 격자는 서버가 바닥과 충돌체로 직접 만듭니다**(`BuildNavGrid`). 바닥(`floors`)이 있으면 칸 가운데가 바닥 위인 칸만 열고(건물 밖은 막힘), 그 위에 벽을 넓혀 막습니다. 파일에도 격자(`rows_data`)가 있지만 칸 가운데만 보고 만들어져서 50cm 칸보다 얇은 20cm 벽이 40% 정도 빠져 있었습니다. 서버는 이동을 막는 정적 충돌체를 **25cm 넓혀서**(`NavWallPaddingCm`, 캐릭터 반지름) 조금이라도 겹치는 칸을 모두 막고, 걸어서 이어지는 칸끼리 **구역 번호**를 붙입니다. 구역이 다르면 A*는 탐색 없이 바로 실패합니다.
- 검사는 두 단계입니다. 게임이 깨지는 문제(스폰·금고·숨는 곳·탈출구·창고 문·감금 자리가 벽 안이거나 의적 스폰에서 걸어서 못 감, 반납 지점을 놓을 방이 4곳보다 적음)는 **서버를 시작하지 않고**, 덜 심각한 문제(경비원 스폰·순찰 지점이 의적 쪽과 안 이어짐, 반납 지점을 놓을 칸이 없는 방)는 **경고 로그**만 남깁니다. 지금 맵은 경고 8개: 문 없는 방 3개(L2, U2, U4) 때문에 경비원 스폰 1·순찰 지점 3개가 안 이어지고 그 방들과 창고(W3)에 반납 지점이 안 생김(클라도 이 방들을 제외).
- 경로 찾기는 경로 격자 위의 **A\***, 시야는 충돌체(3D)로 판정합니다. 경로는 상태가 바뀔 때와 0.5초마다 다시 계산.
- ContentTests의 MapDataTests가 맵 파일이 규칙에 맞는지(금고 후보 10곳, 스폰·상호작용 위치·순찰 지점이 이동 가능한 칸인지) 확인합니다.

| `Content/Game/PathFinder` | 경로 격자 위 A* (8방향, 모서리 끼기 금지, 옥타일 거리) + 경로 다듬기(직선으로 갈 수 있는 중간 점 생략). 작업 배열은 **스레드마다 하나**(`thread_local`)를 세대 번호로 재사용 → 방이 늘어도 메모리가 늘지 않고, 매번 지우는 비용도 없음 |
| `Content/Game/Sight` | 선분 ↔ 충돌체(사각 기둥·원기둥) 3D 시야 검사. 선분을 감싸는 사각형으로 먼저 거르고, 바닥 모양을 지나는 구간의 높이가 충돌체 높이와 겹치면 가려짐 |
| `Content/Game/GuardAI.cpp` | GameWorld의 멤버 함수(파일만 분리): 경비원마다 `GuardBrain`(상태·경로·순찰 지점·마지막으로 본 곳)을 두고 매 틱 ① 소리 ② 보기 ③ 상태 전환 ④ 이동 |

- 틱 순서: `GameWorld::Update` 맨 앞에서 `UpdateGuards`(이동·공격 시작) → 이어지는 엔티티 순회에서 공격 판정·운반 따라가기·발소리 내기. 소리는 다음 틱 AI가 듣는다.
- 경로는 상태가 바뀔 때, 추격 중에는 0.5초마다만 찾습니다(매 틱 찾지 않음).
- 감금: 경비원은 창고 문 앞(`jail.door.interact_pos`)까지 가서 `JailCarried`로 의적을 감금 자리에 놓습니다(창고 안까지 들어가지 않음).
- 시야 검사에서 열고 닫히는 충돌체(창고 문·탈출구)는 건너뜁니다(창살이라 보인다고 봄). 시야를 막지 않는 충돌체(조리대·분수대)도 건너뜁니다.
- 경계 수준이 바뀔 때만 `SC_GUARD_ALERT`(Patrol / Suspicious / Chase+대상 / Search / Stunned). 공격·끄집어내기는 Chase로, 운반은 Patrol + Carrying 비트로 보입니다.
- 규칙 시험(GameRulesTests·GameWorldTests)은 `SetAIEnabled(false)`로 AI를 끄고 경비원을 직접 움직입니다. AI는 GuardAITests에서 따로 시험합니다.

### 8.1 성능 측정과 시연 (P4~P6)

시연에서 성능을 평가하므로, 서버는 **실시간 지표를 화면에 보여 주고, 최적화를 그 자리에서 켜고 끌 수 있게** 만듭니다. 성능 코드(ServerCore)는 그대로 두고 그 위에 측정을 더합니다.

| 지표 | 재는 곳 | 시작 |
|---|---|---|
| 동시 접속, 게임 중인 방 수 | Service, `Content::Perf` | P4 ✔ |
| 틱 처리 시간 (모든 방의 틱, 5초 구간 평균·최대 µs) | GameRoom::Tick 앞뒤 시각 → `Content::Perf` | P4 ✔ |
| AI 시간(틱마다), 경로 탐색 횟수·평균·최대 µs·탐색 칸 수, 시야 검사 수 | GuardAI → `Content::Perf` | P5 ✔ |
| 초당 받은/보낸 패킷, 송신 KB/s | NetStats (이미 있음) | 있음 |
| 프로세스 CPU % | GetProcessTimes | P6 |

- 1초마다 서버 화면에 한 줄, 같은 값을 CSV로도 저장해 보고서 그래프를 만듭니다.
- 최적화(틱마다 보낼 것 묶기, 바뀐 엔티티만 보내는 스냅샷 등)는 콘솔 명령으로 켜고 끌 수 있게 해서 전후 수치를 비교합니다.
- 부하는 `DummyClient bot N`(봇이 방을 만들어 게임까지 진행)으로 만들고, 봇은 서버와 다른 PC에서 돌립니다.
- 시연 장면과 목표는 [ROADMAP.md](../ROADMAP.md)의 "시연 성능 시나리오"를 따릅니다. 설계 계산상 예상치는 CPU 90%에서 3,000~6,000명이며, 그 근처의 첫 병목은 초당 패킷 수입니다.

## 10. 이번 정리에서 뺀 것과 이유

기획서에 없는 기능과, 졸작 수준에서 필요 없는 검증·감시 코드를 덜어 냈습니다. **성능에 관련된 코드는 그대로 둡니다.**

| 뺀 것 | 이유 |
|---|---|
| 프로필·전적, 계정 통계·로드아웃, 방 옵션(맵·난이도·모드), 감정표현, 스킬 공개, 소음, AI 디버그 패킷 | 기획서에 없거나 미정 |
| 전송 빈도 제한(RateLimiter), 로그인 제한 시간·끊는 중 제한 시간(SessionMonitor) | 해킹·악성 접속 방지용. 졸작 수준에서는 필요 없음. 연결 정리는 하트비트 하나로 충분 |
| 서버 이동 검증과 보정 패킷(SC_MOVE_CORRECTION) | 부정행위 방지용. 클라가 보낸 위치를 그대로 씀 |
| 패킷 규칙 위반 통계, 서버 설정(명령줄 옵션) | 감시용. 값은 protocol.h 상수로 고정 |
| `tools/check_layers.ps1`, `GameServer --selftest`, `DummyClient monitor / notice` | 계층 규칙은 이 문서로 지키고, 시험은 ContentTests·DummyClient로 충분 |
| 연결마다 찍던 Info 로그(접속·해제·로그인) | Debug로 내리고 서버는 Info부터 출력. 걸러진 로그는 문자열도 만들지 않음 |
| `accountId` 이름 | 계정이 없으므로 `playerId`로 바꿈 (역할은 같음: 이 연결의 주인이 누구인가) |

**그대로 둔 것**: ServerCore 전체(IOCP, 메모리 풀 ObjectPool/BlockPool, 스레드별 SendBuffer 덩어리, JobQueue/GlobalQueue/JobTimer, 비동기 Logger, NetStats 처리량 지표), 패킷 표와 단계 검사, 하트비트, 브리지 구조, ContentTests.
